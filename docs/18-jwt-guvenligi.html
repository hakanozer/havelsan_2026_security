JWT Güvenliği

JWT formatı claim taşıyan bir token standardıdır; yaygın imzalı JWS formu payload'ı şifrelemez. Güvenlik, algoritma allowlist'i, imza ve claim doğrulaması, issuer/audience/süre kontrolleri ve key lifecycle'a bağlıdır. Projede JWT dependency, token üretimi veya JWT doğrulayan endpoint yoktur.

Neden önemli?

İmza doğrulanmayan veya claim'leri kontrol edilmeyen token, saldırganın değiştirdiği identity/role/expiration verisinin kabul edilmesine yol açabilir. Token çalınırsa süresi boyunca bearer credential gibi kullanılabilir. JWT'de claim payload'ı Base64URL encode edildiğinden secret/password koymak encryption sağlamaz.

Kritik sistemde issuer, audience, subject, expiry/not-before ve signing key rotasyonu identity contract'ının parçasıdır. Token'ı encryption sanmak veya role claim'i tek güvenlik kaynağı kabul etmek yanlış güven duygusu oluşturur.

Saldırı nasıl çalışır?

  1. Uygulama access token üretir ve client'a verir.
  2. Verifier imza doğrulamaz, token'dan gelen `alg` değerini sınırlamaz veya issuer/audience/time claim'lerini kontrol etmez.
  3. Değiştirilmiş/yanlış amaçlı/expired token kabul edilir ya da çalınan token tekrar kullanılır.
  4. Token içindeki role/subject uygulama authorization'ına dönüşür.
  5. Güvenilir library, explicit algorithm allowlist, claim validation, short lifetime, key rotation/revocation stratejisi ve HTTPS doğrulama adımlarını kapatır.

Projemizde nerede?

POM'da JWT library ve `src/main/java` içinde JWT class/endpoint görünmüyor. Mevcut authentication HTTP Basic ve JDBC-backed UserDetails üzerinden SecurityConfig.java:22-42 / CustomerService.java:44-64 ile kurulu.

Kripto key property'lerinin bulunması JWT implementasyonu olduğu anlamına gelmez; CryptoService HMAC ve AES sağlar ama JWT claim parser/signer olarak kullanılmıyor.

ÖNCE / SONRA: projede JWT kodu yok

ÖNCE: JWT token üretme/parse etme kodu olmadığından zayıf proje alıntısı verilemez.

SONRA (Demo Önerisi): JWT seçilecekse Spring Security OAuth2 Resource Server veya doğrulanmış token library'sini dependency olarak ekleyin; issuer/signer ve resource-server validation config'ini ayrı tanımlayın. Algorithm pinning, issuer, audience, expiry/not-before ve authority mapping açık olmalı. Secret/private key'i source properties'e koymayın.

Minimum demo önerisi

  • Paket: com.works.demo.
  • Sınıf: JwtDemoController (yok), verifier config/resource server filter ayrı.
  • Önerilen endpoint: POST /demo/auth/token veya authentication provider flow'u; mevcut değil. Ayrı protected demo endpoint'i, ör. GET /demo/auth/me, yalnızca local profile.
  • Library/version, signing key source ve claims contract'i eğitmen tarafından doğrulanmalı; çalışma zamanı API'si uydurulmayacak.

Demo kodu eklenirse JWT payload'a parolayı veya hassas kişisel veriyi koymayın. JWT imzalı olması payload'ı gizlemez; token içeriği decode edilebilir.

Canlı demo adımları · ancak implementasyondan sonra

  1. Issued token'ın header/payload formatını dummy claims ile decode edin; secret içermediğini gösterin.
  2. Valid token'ın `iss`, `aud`, `exp`, `nbf` ve imzasını verifier'da kontrol ettirin.
  3. Test fixture token'ında tek claim veya imza byte'ı değiştirilince request'in reddedildiğini doğrulayın; payload'ı başka system'e göndermeyin.
  4. Expired token, yanlış audience ve wrong signing key testlerini ekleyin.
  5. Revocation/logout, key rotation ve bearer token log redaction davranışını tasarlayın.
# ÖNERİLEN protected endpoint; proje şu anda bunu sunmuyor:
curl -i http://localhost:8090/demo/auth/me \
  -H 'Authorization: Bearer <yerel-test-token>'
DikkatPlaceholder token çalışmaz; endpoint de henüz yok. Gerçek JWT'yi HTML, shell history, screenshots veya logs içine koymayın.

Önlem mimaride nereye oturur?

Token issuance identity provider/authentication service'te; signature/claim validation SecurityFilterChain/resource server'da; claims-to-authorities mapping policy layer'da; authorization controller/service'de uygulanır. JWT self-contained olduğu için role/permission değişikliği token expiry'ye kadar eski kalabilir; kısa süre/refresh/revocation stratejisi gerekir.

Neden JWT değil session cookie? JWT state'i taşır ama revocation/rotation ve browser storage karmaşıklığı getirir. İhtiyaç yoksa mevcut Spring Security session/basic veya merkezi identity provider daha sade olabilir.

C++ Karşılığı
• C++ REST service'te JWT'yi string parçalayarak doğrulamayın; vetted JOSE/JWT library kullanın.
• Algorithm allowlist'i server config'te sabitleyin; token'ın algorithm claim'ine körü körüne uymayın.
• Signature, issuer, audience, expiry ve not-before doğrulamasını zorunlu kılın.
• Claims'i encrypted sanmayın; kişisel/sensitive data taşımayın.
• Signing key rotation, short lifetime ve revocation/refresh trade-off'unu belirleyin.
• Bearer token'ı logs/URLs içinde taşımayın; TLS kullanın.

Sık yapılan hatalar ve kontrol listesi

  • JWT payload'ını şifreli/gizli sanmak.
  • Signature verify etmeden claims kullanmak.
  • Algorithm/issuer/audience/time claim validation atlamak.
  • Token'a password veya unnecessary PII koymak.
  • Bearer token'ı query string, log veya screenshot'a koymak.
  • Long-lived token için key rotation/revocation planı olmamak.
  • JWT kullanmayı API security'nin tamamı sanmak.

Mini sorular

1. İmzalı JWS token payload'ı gizler mi?

Hayır. İmza bütünlüğü/doğrulama sağlar; payload çoğunlukla Base64URL ile okunabilir biçimdedir.

2. Yalnızca imza doğrulaması yeterli midir?

Hayır. Issuer, audience, expiry/not-before ve authorization mapping de validate edilmelidir.

3. Projede hangi JWT library kullanılıyor?

Envanterde JWT dependency/class/endpoint yok; ayrı, onaylı demo olarak eklenmelidir.
