API attack surface · OWASP API Security

REST API Güvenliği

REST endpoint'leri authorization, DTO sınırı, rate limiting, hata ve log politikalarını birlikte gerektirir. Entity'yi doğrudan request/response olarak kullanmak fazla alan kabul edebilir veya hassas alanları döndürebilir. Projede public registration, entity-returning endpoints, shared rate limiter ve log filtresi var; API versioning görünmüyor.

Neden önemli?

API'ler istemci UI'sının gizlediği alanlara güvenemez. Entity binding fazla property kabul ettirip mass assignment'e; entity response hassas property/metadata sızıntısına; limitsiz/yanlış rate limit ise resource exhaustion'a yol açabilir. Hata mesajı ve log request/credential secret'larını açığa çıkarabilir.

Kritik API'lerde contract versioning, schema limits, authenticated per-object access, rate policy ve telemetry redaction release criteria olmalıdır. OWASP API Security listesi API-specific authorization ve resource consumption kontrolü için başlangıç rehberi sunar.

Saldırı nasıl çalışır?

  1. İstemci JSON body/query/path ile alanlar gönderir.
  2. Controller JPA entity'yi doğrudan bind eder veya entity'yi response olarak döndürür.
  3. Allowlisted DTO/ownership checks yoksa unexpected properties persistence/response'a ulaşır.
  4. Rate control global/yanlış key ile tüm kullanıcıları etkiler; hata/log içeriği hassas veri taşır.
  5. Input/output DTO, explicit field mapping, per-user+IP limits, stable error schema ve redacted audit güven sınırlarını belirginleştirir.

ÖNCE (projede mevcut: entity'yi API boundary'sinde kullanma)

Product save doğrudan `Product` entity bind eder ve response olarak entity döndürür; Note da entity kullanır ve `@Valid` görünmez. Bu pattern tek başına exploit kanıtı değildir; alan allowlist'i ve serialization yüzeyi kontrol edilmelidir.

SONRA (Önerilen Düzeltme)

Projede input/output DTO alternatifi yok. Request DTO sadece client'ın yazabileceği business fields'i, response DTO sadece paylaşılacak fields'i tanımlar; server-generated ID/owner/role/password hash expose edilmez.

public ProductResponse save(@Valid @RequestBody ProductCreateRequest request) {    return productService.saveAndMap(request);}// DTO types/method names are a proposal, not project symbols.

Rate limiting'i endpoint riskine ve user/IP key'ine göre tasarlayın; error handling expected client failure ile internal exception'ı ayırsın. Versioning için proje API contract'ına göre `/v1` veya media type kararı alın, varsaymayın.

Canlı demo adımları

  1. Mevcut `GET /product/list` ve `GET /note/list` endpoint'lerinin response shape'ini test hesabıyla alın; hassas alan çıkmadığını ve production data olmadığını doğrulayın.
  2. Local disposable DB'de `POST /note/save` ile beklenmeyen field/oversize value davranışını inceleyin; kaydı hemen temizleyin.
  3. Limit'i tüm API istekleri arasında paylaşılmış şekilde observe edin; 429 yanıtını ve diğer client etkisini kaydedin.
  4. `POST /customer/register` response'unda `Customer` entity serialization'ı password hash/roles alanı döndürüyor mu kontrol edin; değerleri kaydetmeyin/paylaşmayın.
  5. DTO split önerisinden sonra schema contract testleri ile input field allowlist/output field redaction doğrulayın.

Önlem mimaride nereye oturur?

DTO/controller API contract'ı; service business authorization; repository tenant/ownership query; filter/gateway rate limit ve correlation; `ControllerAdvice` error schema; logging config redaction; API gateway/proxy edge policy katmanıdır. Entity persistence modeli dış contract olmak zorunda değildir.

Public error'da stacktrace/SQL detail vermek yerine stable error code döndürün; ancak sunucu tarafında failure'ı uygun log/audit ile görünür kılın. Hassas parametreyi loglamadan correlation ID ile incident triage yapılabilir.

C++ Karşılığı
• C++ REST endpoint'lerinde input/output contract'ı persistence struct'ından ayırın.
• Allowlist fields ile mass assignment ve over-posting riskini azaltın.
• Per-route/per-principal rate limit ve request size limits uygulayın.
• Error response stable olsun; internal details server-side redacted logda kalsın.
• Versioned API contract ve negative authorization/schema tests tutun.
• Path/file/secret/token alanlarını loglamayın; correlation ID kullanın.

Sık yapılan hatalar ve kontrol listesi

  • JPA entity'yi otomatik API request/response contract yapmak.
  • Entity response içinde password hash/owner/internal fields olup olmadığını unutmak.
  • Global limiter'ı account/IP keyed brute-force control sanmak.
  • Controller advice'te generic exception'ı success-like response'a çevirmek.
  • Client DTO'dan owner/role/ID alanını güvenilir kabul etmek.
  • Note save'de `@Valid` ve body size limitini test etmemek.
  • Versioning ve compatibility planı olmadan response schema değiştirmek.
  • Hassas request/session değerlerini loglamak.

Mini sorular

1. Input DTO kullanımı bütün mass assignment riskini çözer mi?

Alan yüzeyini daraltır; authorization, ownership validation ve service policy yine gerekir.

2. Entity response API'de hangi gizli riski doğurabilir?

İstenmeyen alanlar, ilişkiler veya password hash gibi internal properties JSON'a serialize olabilir; response DTO explicit allowlist sağlar.

3. Projedeki rate limiter kullanıcı başına mı?

Görünen konfigürasyon tek RateLimiter bean'i ve filter'da ortak acquire çağrısı; user/IP key'i gösterilmemiştir.
