Broken Access Control · object-level authorization

Alıştırma: Authorization Bypass, IDOR ve BOLA

Authentication kimliği belirler; authorization isteğin hedef kaynağa ve işleme izinli olup olmadığını denetler. IDOR/BOLA'da kullanıcı geçerli kimlikle başka nesnenin kimliğini/ID'sini değiştirerek erişir. Bu projede URL rol kontrolleri vardır ve kayıt isteği rol alanı taşır; ancak ID ile kullanıcı kaydı getiren endpoint bulunmadığından IDOR örneği mevcut değildir.

Neden önemli?

Yetki kararı yalnızca “kullanıcı giriş yaptı mı?” ile sınırlı kalırsa, bir rol veya nesne kimliğini değiştirmek başka kullanıcının verisine erişim sağlayabilir. BOLA özellikle REST API'lerde her object ID'nin ayrı ayrı sahiplik/tenant kontrolünden geçirilmemesiyle oluşur. Sonuç kayıt gizliliği, bütünlüğü ve tenant ayrımının kaybıdır.

Kritik sistemlerde her işlemde server-side identity, function-level role ve object ownership/tenant bağlamı beraber kontrol edilmelidir. OWASP API Security Top 10'da BOLA ayrı API riskidir; server-side policy, client gizleme veya tahmin edilmesi zor ID'lerin yerine geçer.

Saldırı nasıl çalışır?

  1. Kullanıcı normal authentication ile API'ye ulaşır.
  2. İstek içindeki rol, hesap ID'si, note ID veya tenant alanını değiştirir.
  3. Sunucu yalnızca kimliği doğrular ya da genel role bakar; nesnenin o kullanıcıya ait olduğunu sorgu/policy ile doğrulamaz.
  4. Başka kullanıcı nesnesi okunur/değiştirilir veya ayrıcalıklı role giden yol açılır.
  5. Server-side role assignment ve her object operation'da ownership check saldırı zincirini keser.

Projemizde nerede?

  • Role-gated path rules: SecurityConfig.java:22-34.
  • Public registration'da `roles` alanı: CustomerRegisterRequestDto.java:16-29.
  • Request DTO'nun entity'ye map edilip kaydedilmesi: CustomerService.java:38-42.
  • UserDetails authorities DB rol adlarından yükleniyor: CustomerService.java:45-64.

/customer/register anonymous açık, request DTO roles alıyor ve service map ediyor. Bu bir yüksek riskli tasarım işaretidir; ModelMapper/H2 persistence ve `Role` ilişkisinin runtime davranışı test edilmeden bu akışın kesin privilege escalation verdiği iddia edilmemeli.

Projede `/{id}` üzerinden kullanıcıya bağlı nesne alan endpoint bulunmadı; gerçek IDOR/BOLA vakası gösterilemez.

ÖNCE (projede mevcut: istemciden role alan kayıt DTO'su)

Gerçek kod, `roles`'u public kayıt request'inin alanı yapıyor. Burada alıntılanan satırlar tasarım riskidir; rolün DB'de başarıyla oluşturulup yetki verdiği ayrıca entegrasyon testiyle doğrulanmalıdır.

Kaynak: src/main/java/com/works/dto/CustomerRegisterRequestDto.java:16-29, kayıt akışı CustomerService.java:38-42.

public class CustomerRegisterRequestDto implements Serializable {    @NotNull    String email;    String password;    @NotNull    @Size(min = 1, max = 5)    List<RoleDto> roles;}

Mevcut `@Valid` kayıt endpoint'inde bu alan kabul edilir. Girdi sınırı doğrulaması uzunluk sınırlar ama kullanıcının hangi role atanabileceğini yetkilendirmez.

SONRA (Önerilen Düzeltme)

Projede güvenli kayıt alternatifi yok. Public signup DTO'sundan roles alanını çıkarın; server-side sabit least-privilege rol atayın. Admin role değişimi ayrı, yetkili iş akışı ve audit altında olsun. Öneri snippet'i:

Customer customer = modelMapper.map(request, Customer.class);customer.setRoles(List.of(defaultRegistrationRole));return customerRepository.save(customer);

Bu öneri kodu gerekli role lookup/transaction yönetimini atlar ve projede mevcut değildir; gerçek uygulama rol entity'sini trusted DB kaynağından alıp signup DTO'sunda role kabul etmemelidir.

Canlı demo adımları

  1. Yalnızca local disposable H2 ile `/customer/register` contract'ını inceleyin. Request DTO'daki role alanını ve servis mapping'ini gösterin; önce mevcut seed/DB constraint davranışını kaydedin.
  2. Aşağıdaki JSON'daki boş `roles` listesi `@Size(min=1)` nedeniyle validation aşamasında reddedilmelidir; bu yalnızca input validation kontrolüdür, ModelMapper akışını test etmez. Mapping'i doğrulamak için önceden hazırlanmış local role fixture gerekir; veritabanı ilişki/persistence sonucunu gözleyin ve kesin privilege escalation varsaymayın.
  3. Policy kontrolünü `GET /product/list` ve `GET /note/list` ile denetleyin: anonim/yanlış role erişmemeli, yetkili test user erişebilmelidir. Kaynakta credential yok.
  4. IDOR için proje endpoint'i olmadığını belirtin. Ayrı önerilen demo gerekiyorsa NoteOwnershipDemoController ve GET /demo/notes/{id} oluşturup owner/tenant check'i tasarlayın; bu endpoint şu an yok.
# Mevcut, gerçek endpoint: yalnızca yerel disposable DB'de
curl -i -X POST http://localhost:8090/customer/register \
  -H 'Content-Type: application/json' \
  -d '{"email":"yerel-ogrenci@example.test","password":"gecici-demo-parolasi","roles":[]}'

# Mevcut, gerçek endpoint; erişimi yalnızca test hesabıyla sınayın:
curl -i http://localhost:8090/product/list
DikkatÖrnek kayıt JSON'u role ekleyerek yetki kazanma payload'ı değildir; validation minimum rol sayısını şart koşuyor. Rol binding/persistence etkisini kontrollü test edin. Gerçek/ortak veritabanına kayıt denemesi yapmayın.

Önlem mimaride nereye oturur?

Function-level authorization SecurityFilterChain veya method security'de; object-level check service/repository query'de; role provisioning kayıt/admin service'inde uygulanır. Controller DTO'su güven sınırıdır ama tek başına sahiplik politikasını garanti etmez. ID'yi UUID yapmak veya UI'da butonu gizlemek access control değildir.

Neden sadece `hasRole` alternatifi yetmez? Rol endpoint'e erişimi tanımlar; hangi kaydın o role ait kullanıcı tarafından erişilebileceği object authorization gerektirir.

C++ Karşılığı
• C++ REST handler'ında kimlik doğrulamadan sonra her route için function ve object-level authorization uygulayın.
• Request DTO'dan role/owner/tenant alanlarını doğrudan güvenilir modele map etmeyin.
• DB sorgusuna kullanıcı kimliği/tenant kapsamını server-side ekleyin.
• ID'nin tahmin edilemezliği access control yerine geçmez.
• Deny-by-default ve negatif testleri (başka kullanıcının ID'si) CI'da çalıştırın.
• Framework API'sini seçilen Boost.Beast/Crow/Drogon sürümünde doğrulayın.

Sık yapılan hatalar ve kontrol listesi

  • Authentication'ı authorization sanmak.
  • Public register request'inde role/permission alanı kabul etmek.
  • ModelMapper/JSON binding'i güvenli allowlist gibi varsaymak.
  • Collection endpoint'ini koruyup nesne ID endpoint'inde ownership check yapmamak.
  • Tenant ID'yi istemciden alıp server identity ile karşılaştırmamak.
  • Negatif test yazmadan sadece izinli kullanıcının başarı testini yapmak.
  • Mevcut olmayan IDOR endpoint'ini proje referansıymış gibi anlatmak.

Mini sorular

1. Projede IDOR/BOLA endpoint'i var mı?

Mevcut controller'lardaki route'larda object ID ile tekil kullanıcı nesnesi okuma/değiştirme endpoint'i görünmüyor; IDOR demosu ek öneri olmalı.

2. `@Size` ile roles listesi doğrulamak rol atamasını güvenli hale getirir mi?

Hayır. Boyut kontrolüdür; bu kullanıcının hangi role sahip olabileceğini server-side policy belirlemelidir.

3. `hasRole("product")` BOLA'yı engeller mi?

Tek başına değil. Bu URL/fonksiyon erişimini denetler; user'ın istediği object üzerinde sahiplik/tenant kontrolü de gerekir.
