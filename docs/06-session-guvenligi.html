Session id is a bearer credential · OWASP A07

Session Güvenliği

Session Hijacking, saldırganın geçerli session kimliğini ele geçirip kullanıcı adına istek yapmasıdır. Tarayıcı cookie’si bu kimliği otomatik gönderdiğinden TLS, cookie nitelikleri, oturum yaşam döngüsü ve CSRF koruması birlikte tasarlanmalıdır. Projede filtre her istekte session açıyor/alıntılıyor ve SessionId’yi logluyor; cookie flag’leri veya timeout ayrıca yapılandırılmamış.

Neden önemli?

Session ID, çoğu session tabanlı sistemde kullanıcı adına işlem yapmaya yeterli bir bearer değerdir. Log, browser storage, insecure transport veya XSS ile ele geçirilirse saldırgan parola bilmeden oturumu devralabilir. Kurumsal/kritik sistemde bu, kullanıcının yetkisi dahilindeki işlemlerin taklit edilmesine neden olabilir.

HttpOnly JavaScript'in cookie'yi okumasını engeller; Secure yalnızca HTTPS üzerinden gönderir; SameSite cross-site gönderimi sınırlar. Hiçbiri tek başına Session Hijacking'i tüm yollarıyla önlemez.

Saldırı nasıl çalışır?

  1. Uygulama session oluşturur ve tarayıcıya session cookie verir.
  2. Kimlik HTTPS dışında taşınır, JavaScript'e açılır, loga yazılır veya session fixation ile saldırganın bildiği değer kullanılır.
  3. Saldırgan kopyalanan session ID ile aynı servise istek yollar.
  4. Sunucu session geçerli olduğu için isteği o kullanıcıya bağlar.
  5. TLS, cookie flag'leri, session ID yenileme, idle/absolute timeout, logout invalidation ve log redaction farklı aşamalarda zinciri kırar.

Projemizde nerede?

Gerçek referans: src/main/java/com/works/config/FilterConfig.java:51-69. Filtre `getSession().getId()` çağırıp session ID'yi log mesajına koyuyor. `getSession()` yoksa yeni session oluşturabilir; filter'ın güvenlik zincirine göre sırası ve istemciye cookie gönderimi çalışma zamanı testiyle doğrulanmalı.

Cookie flag, session timeout veya fixation strategy için [SecurityConfig.java](../src/main/java/com/works/config/SecurityConfig.java) ve [application.properties](../src/main/resources/application.properties) içinde açık ayar görünmüyor. Ayar görünmemesi framework default'unun ne olduğunu kanıtlamaz; etkili runtime config ölçülmelidir.

ÖNCE (projede mevcut: session ID loglama)

Bu kod session ID'yi operasyonel loga yazar. Log erişimi, kopyalanması ve saklama süresi session anahtarına erişim gibi değerlendirilmelidir.

SONRA (Önerilen Düzeltme)

Projede session ID'yi loglamayan alternatif bulunmuyor. Logu ihtiyaca göre session dışı correlation ID ve gerekli minimum metadata ile sınırlandırın; gerekiyorsa hassas değeri redakte edin. Aşağıdaki örnek öneridir, proje alıntısı değildir.

log.info("Request: {}, user: {}", correlationId, username);// Session ID, access token ve credential loglanmaz.

Cookie ve oturum yaşam döngüsü

  • HttpOnly: JavaScript'in cookie'yi okumasını sınırlar; XSS'i tamamen çözmez.
  • Secure: yalnızca HTTPS üzerinden gönderim; TLS konfigürasyonuna bağlıdır.
  • SameSite: Lax/Strict/None seçimi cross-site akış gereksinimine bağlıdır; CSRF önlemlerinin tamamı değildir.
  • Session fixation: authentication/privilege değişiminde session ID yenileme davranışını test edin; framework'ün etkili strategy'sini doğrulayın.
  • Timeout: inactivity timeout ve gerekirse absolute lifetime tanımlayın; server-side session invalidation çalışsın.
  • Logout: browser cookie'sini silmenin yanında server-side session'ı da invalidate edin.

Neden cookie flag tek başına alternatif değil? Cookie theft yalnızca JavaScript ile olmaz; network, log, endpoint ve session lifecycle da korunmalıdır.

Canlı demo adımları

  1. Yerel API'de POST /customer/login çağırıp response header'larını ve browser cookie storage'ını gözleyin. Gerçek test kullanıcısı yoksa kayıt/seed'i eğitmen kontrollü oluşturmalıdır.
  2. Uygulamaya gelen aynı request için `logs/application.log`/konsolda SessionId alanının olup olmadığını kontrol edin; değer paylaşmayın veya kopyalamayın.
  3. `curl -i` ile cookie flag'lerini response `Set-Cookie` üzerinde inceleyin. Flag görünmüyorsa bunu “runtime'da yok” diye doğrulamadan önce deployment/proxy ayarlarını da kontrol edin.
  4. Öneri sonrası session ID loglarının kaldırıldığını ve logout/timeout sonrası eski session'ın artık kabul edilmediğini test planına alın. Mevcut projede logout endpoint'i yok.

Önlem mimaride nereye oturur?

Cookie flag ve session policy security/config katmanında; ID yenileme authentication lifecycle'da; logout/timeout session repository/servlet katmanında; log redaction logging/filter sınırındadır. TLS ve CSRF cookie tabanlı browser auth ile birlikte çalışır. `HttpOnly` output encoding yerine, `SameSite` de authorization yerine geçmez.

C++ Karşılığı
• C++ HTTP servisinde session ID de bearer secret'tır; URL, log veya plaintext transport'a koymayın.
• HTTPS zorunlu tutun ve session cookie'de HttpOnly/Secure/SameSite politikalarını ayarlayın.
• Session kimliğini tahmin edilemez üretin; authentication/privilege değişiminde yenileyin.
• Idle timeout, logout invalidation ve CSRF kontrollerini server-side uygulayın.
• Framework cookie API'si seçime göre değişir; Boost.Beast/Crow/Drogon kullanımında gerçek API'yi doğrulayın.
• Session/token değerlerini test ve telemetry kayıtlarından da redakte edin.

Sık yapılan hatalar ve kontrol listesi

  • Session ID veya cookie değerini loglamak.
  • HttpOnly'yi XSS önlemi olarak tek başına görmek.
  • Secure flag ayarlayıp TLS'in gerçekten aktif olduğunu varsaymak.
  • SameSite'i CSRF için tek kontrol kabul etmek.
  • Login sonrası session ID yenilenmesini test etmemek.
  • Logout'ta yalnızca browser cookie'sini silmek.
  • Session timeout ve invalidation'ı tanımlamamak.

Mini sorular

1. HttpOnly cookie Session Hijacking'i tamamen engeller mi?

Hayır. JavaScript okumasını azaltır; log sızıntısı, ağ, malware ve diğer token erişim yolları ayrı savunma ister.

2. `getSession()` ile `getSession(false)` davranışı neden önemlidir?

İlki session yoksa oluşturabilir; ikincisi yalnızca mevcut session'ı döndürür. Sırf log için session açmak gereksiz state ve cookie üretebilir.

3. SameSite ayarı CSRF token'ı her durumda gereksiz kılar mı?

Hayır. Browser/istemci uyumu ve cross-site kullanım farklıdır; token ve origin kontrolleri tehdit modeline göre hâlâ gerekebilir.
