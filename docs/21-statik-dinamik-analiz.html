Neden önemli?

Manual code review tek başına tüm path'leri, dependency advisory'lerini veya input sınırlarını kaçırabilir. SAST yanlış/şüpheli kod pattern'lerini, SCA vulnerable dependency ve lisans politikasını, DAST ise çalışan uygulamanın dışarıdan gözlenen davranışını hedefler. Her araç farklı kör nokta ve false positive taşır.

Kritik/savunma yazılımında tekrarlanabilir CI quality gate, test evidence ve exception owner/süreç izi sağlar. Scanner sonucu “güvenli” sertifikası değildir; bulgular threat model ve manuel incelemeyle doğrulanır.

Risk nasıl gözden kaçabilir?

  1. Yeni feature veya dependency eklenir.
  2. Build yalnızca compile/context startup test eder; security rule/edge case çalıştırılmaz.
  3. Weak pattern, vulnerable transitive component veya runtime endpoint misconfiguration release'e ulaşır.
  4. Deploy sonrası veri veya erişim etkisi ortaya çıkar.
  5. SAST + unit/integration + SCA + isolated DAST farklı aşamalarda sinyal üretir; reviewer sonuçları triage eder.

Projemizde nerede?

  • Build/dependencies: pom.xml. Test dependency starter'ları mevcut, static security plugin görünmüyor.
  • Mevcut test: MainAppTests.java:6-12, `contextLoads()`.
  • Build output'ta `target/` var; bu scanner setup veya clean CI pipeline kanıtı değildir.
  • C++ source/build configuration workspace'te yok; C++ tools öneri olarak kalır.

SONRA (Önerilen Düzeltme)

Proje build'ine security scanner bağlanmamış. CI'da compile/test, static bug analysis, dependency scan ve local ephemeral app üzerinde DAST'i ayrı job'lar yapın. Scanner policy thresholds/suppression owner'ı project risk modeline göre belirlenmelidir.

1. Compile + unit/integration/security tests2. SAST: SpotBugs + FindSecBugs (Java), SonarQube analysis3. SCA: OWASP Dependency-Check; reviewed dependency update4. DAST: OWASP ZAP against isolated local test deployment5. Triage: severity, reachability, owner, remediation deadline

Canlı demo adımları

  1. Mevcut smoke test'i çalıştırın: Maven wrapper destek dosyaları eksik olduğu için bu checkout'ta yerel `mvn test` kullanılmalıdır; datasource password config gerekebilir.
  2. SpotBugs/FindSecBugs ya da Dependency-Check'i local/CI job olarak ayrıca kurup project source üzerinde scan çalıştırın; output'u review edin, findings'i otomatik açık olarak etiketlemeyin.
  3. App'i disposable local profile'da başlatın; ZAP passive/baseline taramasını yalnızca `localhost` üzerinde yapın. Üretim/public target kullanmayın.
  4. C++ modülü yoktur; clang-tidy/cppcheck/sanitizer entegrasyonunu ayrı C++ demo reposunda gösterin.
  5. False positive/exception için owner, gerekçe, expiry ve follow-up test kayıt altına alın.

Önlem mimaride nereye oturur?

SAST/SCA commit/CI build gate'inde; unit/integration tests developer/CI feedback loop'unda; DAST isolated staging'de; manual threat model/review release governance'da durur. Tek scanner tüm vulnerability class'larını bulamaz; findings risk/false positive/reachability ile triage edilir. Suppression kalıcı sessiz bypass olmamalı; sorumlu ve bitiş koşulu taşımalı.

C++ Karşılığı
• `clang-tidy` ve `cppcheck`'i compile/review pipeline'a ekleyin.
• AddressSanitizer/UBSan ile test build'lerinde memory/undefined behavior saptayın.
• Fuzzing (libFuzzer/AFL++) parser/API sınırlarını test eder; corpus ve timeout yönetin.
• Coverity gibi SAST, Valgrind gibi runtime araçları farklı sinyal üretir.
• Findings'i severity, reachability ve false positive kanıtıyla triage edin.
• SEI CERT C++/MISRA kuralları ekip standardına göre seçilsin.

Sık yapılan hatalar ve kontrol listesi

  • Context-load testini security test coverage saymak.
  • SAST'ı DAST/SCA ile karıştırmak.
  • Scanner'daki tüm bulguları doğrulamadan gerçek risk veya false positive ilan etmek.
  • Suppressionsız severity threshold'ları build'e aniden uygulamak.
  • DAST'i yanlış/prod hedefte çalıştırmak.
  • Dependency scan sonuçlarını reachability olmadan otomatik kabul/ret etmek.
  • C++ sanitizer'ı production safety guarantee sanmak.

Mini sorular

1. SpotBugs ve ZAP aynı analiz türü müdür?

Hayır. SpotBugs static analysis; ZAP çalışan web uygulamasını dynamic test eder.

2. Dependency-Check finding'i her zaman reachable exploit anlamına mı gelir?

Hayır. Dependency/advisory match'i risk triage, version/path/reachability ve impact review gerektirir.

3. AddressSanitizer code review yerine geçer mi?

Hayır. Test execution sırasında memory error saptar; design, authorization ve untested path'i kanıtlamaz.
