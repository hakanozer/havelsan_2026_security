Browser ambient credentials · OWASP CSRF Prevention Cheat Sheet

Cross-Site Request Forgery (CSRF)

CSRF, browser'ın otomatik gönderdiği cookie veya başka ambient credential'ı kullanan, istemcinin niyet etmediği state-changing istektir. Sunucu geçerli session görür ama isteğin kullanıcının uygulamasından geldiğini doğrulamaz. Projede SecurityFilterChain CSRF'i açıkça kapatıyor; REST API'nin browser/cookie kullanım modeli bilinmeden bu karar güvenli varsayılamaz.

Neden önemli?

Browser hedef origin için session cookie'sini otomatik ekler. Kullanıcı başka bir siteyi açtığında, o sayfa browser'ı state değiştiren hedef isteğe yönlendirebilir. Sunucu yalnızca cookie ile auth yapıyorsa isteği geçerli kullanıcıdan gelmiş gibi işleyebilir. Etki, kullanıcının yetkisiyle kayıt değiştirme veya işlem başlatma olabilir.

CSRF, XSS'ten ayrıdır: XSS hedef origin içinde script çalıştırır; CSRF kullanıcının browser'ını cross-site isteğe yönlendirir. Anti-CSRF token, SameSite, Origin/Referer kontrolleri risk modeline göre katmanlı uygulanır.

Saldırı nasıl çalışır?

  1. Kullanıcı hedef uygulamada authenticated session açar.
  2. Browser, başka origin'deki içeriğin başlattığı isteğe otomatik credential ekler.
  3. Sunucu cookie'yi geçerli bulur; niyet/origin/token kontrolü yapmıyorsa state change'i kabul eder.
  4. İşlem kullanıcı adına gerçekleşir.
  5. Synchronizer token/double-submit, SameSite defense-in-depth ve Origin/Referer validation isteğin meşruiyetini doğrular.

Projemizde nerede?

src/main/java/com/works/config/SecurityConfig.java:22-34 içinde `.csrf(csrf -> csrf.disable())` var. Projede form login disable edilmiş, HTTP Basic açılmış. Session/filter davranışı için FilterConfig.java:51-69 ayrıca incelenebilir.

Bu config'in exploit edilebilir CSRF olduğunu tek başına kanıtlamaz: browser/credential kullanım biçimi ve endpoint etkileri değerlendirilmelidir. Ancak CSRF disable kararı, tarayıcı otomatik credential gönderiyorsa korumayı kaldırır.

).formLogin(login -> login.disable()).csrf(csrf -> csrf.disable()).build();

SONRA (Önerilen Düzeltme)

Projede token korumalı alternatif yok. Browser tabanlı, cookie/session veya browser'ın otomatik eklediği Basic credential kullanan state-changing API için CSRF korumasını etkin tutun ve Spring Security'nin token mekanizmasını istemciyle entegre edin. Aşağıdaki akış pseudo-code'dur; Spring Security 6/7 API ve SPA token davranışı kullanılan 4.1.0 stack'te ayrıca doğrulanmalıdır.

http.csrf(csrf -> csrf /* token repository + request handler policy */);// Browser state-changing request: server-issued token + Origin checks.// CSRF'i ancak credential modeli ve threat model uygunsa devre dışı bırak.

OWASP CSRF Prevention Cheat Sheet yaklaşımı

  • Synchronizer Token: stateful session için server-generated unpredictable token'ı state-changing istekte doğrula; URL/log içine koyma.
  • Signed Double-Submit Cookie: stateless tasarımda cookie/header çiftini cryptographic binding ile doğrula; basit eşleşen cookie tek başına saldırgan tarafından set edilebilir.
  • SameSite: cookie'nin cross-site gönderimini sınırlar; browser uyumu ve cross-site iş akışıyla test edin. Tek kontrol olarak kabul etmeyin.
  • Origin/Referer: state-changing browser isteklerinde beklenen origin'i doğrulayın; proxy/header trust sınırını belirleyin.
  • Custom header: API'de token'ı custom request header ile istemek, browser CORS preflight davranışıyla birlikte yardımcı olabilir; permissive CORS ile etkisini bozmayın.
  • REST/JWT: token yalnızca JS tarafından eklenen Authorization header'da ve cookie gibi otomatik credential yoksa classic CSRF riski azalır. JWT cookie'de tutuluyorsa CSRF riski sürer; Basic Auth da browser tarafından otomatik gönderilebilir.

OWASP cheat sheet yaklaşımında CSRF token temel savunmadır; SameSite ve origin kontrolü defense-in-depth'tir. XSS saldırganın origin içinde kod çalıştırmasına izin verebildiğinden CSRF token'ı tek başına XSS'e karşı koruma değildir.

Canlı demo adımları

  1. Projede `POST /note/save` state-changing endpoint'ini ve CSRF disable config'ini gösterin; sadece local/izole instance kullanın.
  2. Önce CSRF token beklenmediğini kaynak config'ten belirleyin. Browser session/basic credential'ın gerçekten otomatik gönderilip gönderilmediğini runtime network tabında doğrulayın.
  3. CSRF etkinleştirilmiş yerel demo profili önerilirse token fetch + valid/invalid request'i kıyaslayın. Projede CSRF token endpoint/client yok; konfigürasyon eklenmeden bu adımlar çalışmaz.
  4. `Origin` allow/deny testini aynı origin ve farklı origin simülasyonuyla yapın; CORS kararını CSRF yerine kullanmayın.
# Mevcut gerçek state-changing endpoint; local testte CSRF token olmadığı için sonucu gözlemleyin:
curl -i -X POST http://localhost:8090/note/save \
  -H 'Content-Type: application/json' \
  -d '{"title":"CSRF test","content":"yalnızca local"}'
# Bu curl komutu browser CSRF saldırısını simüle etmez; token ve cookie modeli ayrıca gerekir.
Eğitmen NotuProje endpoint'i Basic auth/role şartı ve rate limitten etkilenebilir. `curl` browser'ın ambient cookie davranışını modellemez; demo için browser tabanlı test client gerekebilir.

Önlem mimaride nereye oturur?

SecurityFilterChain token/origin doğrulamasını merkezi uygular; cookie config SameSite davranışını belirler; controller/service state-changing iş kurallarını korur; CORS farklı origin'in script erişimini sınırlar. CORS, CSRF koruması değildir: browser request gönderebilir ama response okunmasını engelleyebilir; bu her state change'i önlemez.

CSRF'i kapatmanın alternatifi “REST API olduğu için güvenli” varsayımı değil; credential'ın browser tarafından otomatik gönderilip gönderilmediğini belirleyip token veya uygun origin guard uygulamaktır.

C++ Karşılığı
• C++ HTTP servisinde browser cookie/session auth kullanılıyorsa state-changing istekleri CSRF token ile koruyun.
• SameSite ve Origin/Referer doğrulamasını defense-in-depth olarak tasarlayın.
• JWT yalnızca otomatik cookie'de taşınıyorsa CSRF riskini yok saymayın.
• CORS allowlist'i dar tutun; `Access-Control-Allow-Origin: *` credential koruması değildir.
• Custom header/token yaklaşımını seçilen framework ve browser akışında doğrulayın.
• XSS'e karşı output encoding ayrıca gerekir; CSRF token XSS'i çözmez.

Sık yapılan hatalar ve kontrol listesi

  • “REST/JSON ise CSRF olmaz” demek.
  • JWT kullanıp cookie/Basic ambient credential modelini incelememek.
  • SameSite'ı tek başına yeterli saymak.
  • Unsigned double-submit cookie kullanmak.
  • CORS'u CSRF kontrolü sanmak.
  • Token'ı URL veya loga koymak.
  • CSRF'i kapatıp bunun nedenini endpoint/credential modeliyle belgelememek.

Mini sorular

1. JWT kullanan bir API her durumda CSRF'den muaf mıdır?

Hayır. JWT cookie ile taşınıyorsa browser otomatik gönderir; Authorization header'a JS ile eklenen bearer token farklı bir credential modelidir.

2. CORS CSRF token ile aynı koruma mıdır?

Hayır. CORS response erişimini düzenler; browser'ın bazı state-changing istekleri göndermesini tek başına engellemez.

3. Projede CSRF token endpoint'i var mı?

Yok. SecurityConfig CSRF'i disable ediyor; token akışlı demo öneri/iyileştirme olarak eklenmelidir.
