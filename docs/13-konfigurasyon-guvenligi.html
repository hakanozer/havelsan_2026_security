Secure by environment · OWASP A05:2021

Konfigürasyon Güvenliği

Güvenli kod, güvensiz deployment ayarlarını telafi edemez. Secret'ın repository'de tutulması, debug SQL'in açılması, profile'ların karışması veya yönetim yüzeyinin açık kalması uygulamanın gerçek riskini artırır. Bu projede H2/JPA ayarları ve kripto key property'leri kaynakta var; SSL/Actuator/H2-console etkinleştirmesi ayrıca görünmüyor.

Neden önemli?

Uygulama aynı binary ile farklı ortamlara deploy edilir; profile ve environment değiştikçe güvenlik varsayımları değişir. Secret yanlışlıkla source control'a girerse erişimi olan herkes secret'ı kullanabilir; debug SQL ve geniş hata mesajı veri/şema sızdırabilir; açık yönetim endpoint'i kontrol yüzeyi olur. Kritik sistemlerde config change ve secret rotation da denetlenebilir yaşam döngüsüdür.

Secret manager, minimal profile ve least privilege, secret'ı repodan kaldırır; fakat erişim politikası, rotation ve log redaction olmadan tek başına yeterli değildir.

Saldırı nasıl çalışır?

  1. Developer key/password gibi değerleri config'e commit eder veya production'a dev profile taşır.
  2. Repository/history/build artifact/log üzerinden değer ifşa olur ya da debug/H2/management yüzeyi açık kalır.
  3. Saldırgan credential'ı veya hassas diagnostik çıktıyı ele geçirir.
  4. DB/crypto/admin erişimi veya bilgi sızıntısı ortaya çıkar.
  5. Secret'ı environment/secret store'dan al, profile bazında güvenli default uygula, prod test ve rotation ekle.

Projemizde nerede?

application.properties:4-18: `server.port=8090`, file H2, `ddl-auto=update`, `show-sql=true`, AES/HMAC property anahtarları. Anahtar değerleri dokümanda bilinçli olarak gösterilmemiştir.

  • CryptoService.java:21-25 anahtarları `@Value` ile okuyor.
  • DBService.java:11-34 DB properties'ini DataSource'a aktarıyor.
  • POM'da H2 console starter vardır; properties'te console enable ayarı görünmüyor. Dependency varlığı console'un enabled olduğunu kanıtlamaz.
  • Actuator dependency ve management endpoint config'i envanterde görünmedi.

ÖNCE (projede mevcut: development-risk konfigürasyonları)

Kaynakta sabit anahtar değerleri olduğundan bunları dokümana kopyalamıyoruz; aşağıda yalnızca key adları ve yer tutucu gösterilmiştir. Gerçek dosyada değerler bulunur. JPA debug/update ayarları eğitim ortamına özgü kabul edilmelidir.

Kaynak: src/main/resources/application.properties:12-18

# JPA Configspring.jpa.hibernate.ddl-auto=updatespring.jpa.show-sql=true# Security Key Configsecurity.crypto.aes-key=<repo'da tanımlı değer; burada redakte edildi>security.crypto.hmac-key=<repo'da tanımlı değer; burada redakte edildi>

SONRA (Önerilen Düzeltme)

Projede profile/secret-store çözümü yok. Secret'ı externalize edin; schema migration ve SQL logging ayarlarını profile'a göre yönetin:

security.crypto.aes-key=${SECURITY_CRYPTO_AES_KEY}security.crypto.hmac-key=${SECURITY_CRYPTO_HMAC_KEY}# Üretim ortamında schema migration aracı ve kontrollü DDL seçin.# SQL diagnostics yalnızca izole dev profile'da etkin olsun.

Bu properties önerisidir; gerçek secret values deployment secret store/CI ortamından sağlanmalı. H2 Console/Actuator gerekliyse ayrı management access policy, ağ kısıtı ve kimlik doğrulamasıyla etkinleştirin; production'da gereksizse dependency/feature'ı kapatın.

Canlı demo adımları

  1. Source properties'te key isimlerini ve riskli ayarları bulun; key değerlerini ekrana yansıtmayın.
  2. Uygulamanın config binding'ini local test ortamında environment variable ile override edin; credential'ı terminal history'ye yazmamaya dikkat edin.
  3. Dev/test profile'da SQL log davranışını gösterin. Üretim profili için `show-sql`, schema update ve secret source policy'yi review edin.
  4. H2 Console/Actuator için önce dependency ve effective config'i doğrulayın; özellik açıkmış gibi varsaymayın.
  5. Secret rotation ve restart sonrası uygulamanın yeni değeri kullandığını kontrollü secret ile test edin.
# Yalnızca local test için; gerçek değerleri komut geçmişine eklemeyin
SPRING_PROFILES_ACTIVE=local \
SECURITY_CRYPTO_AES_KEY='<yerel-secret-store-değeri>' \
SECURITY_CRYPTO_HMAC_KEY='<yerel-secret-store-değeri>' \
mvn spring-boot:run
DikkatProperty conversion ve environment naming'i Spring Boot konfigürasyonunda doğrulayın. Secret'ı shell history, CI log, screenshot veya HTML içine kopyalamayın.

Önlem mimaride nereye oturur?

Config kaynağı/profiles uygulama başlangıcında; secret store ve IAM platform katmanında; SQL diagnostics/schema migration build/deployment katmanında; H2/Actuator network/management katmanında korunur. Environment variable kullanmak source control riskini azaltır fakat erişim yetkisi, secret encryption at rest ve rotation yine gerekir.

Neden yalnızca dosyayı silmek yeterli değil? Secret git history, build log ve deployed artifact'te kalabilir; exposed secret rotate edilmeli ve tüm kopyalar/erişimler incelenmelidir.

C++ Karşılığı
• C++ uygulamasına key/password sabitlemeyin; secret manager veya kontrollü environment/config injection kullanın.
• Runtime config'i tipli doğrulayın; bilinmeyen profile ve eksik secret'ta açık hata verin.
• Debug logging, management socket ve test endpoint'lerini release profile'da kapatın.
• File permissions ve process environment erişimini least privilege ile sınırlayın.
• Secret rotation, redaction ve incident response'u deploy pipeline'a bağlayın.
• SEI CERT/MISRA güvenli config ilkeleriyle review edin.

Sık yapılan hatalar ve kontrol listesi

  • Secret'ı application.properties ya da git history'de bırakmak.
  • Production'da `show-sql` veya detaylı error açmak.
  • `ddl-auto=update`'ı migration governance yerine kullanmak.
  • H2/Actuator dependency'sini endpoint'in kesin açık/kapalı kanıtı sanmak.
  • Local/test profile'ını production'a taşımak.
  • Environment variable'ı her sistemde otomatik secret store sanmak.
  • Exposed key'i sadece dosyadan silip rotation yapmamak.

Mini sorular

1. Anahtar property'lerini env variable'a taşımak secret yönetimini tamamen çözer mi?

Hayır. Process environment erişimi, CI logları, secret store permission, rotation ve redaction da kontrol edilmelidir.

2. H2 console starter bulunması console'un açık olduğunu kanıtlar mı?

Hayır. Etkin dependency/config/runtime davranışı ayrıca doğrulanmalıdır.

3. Kaynakta yanlışlıkla yayımlanan crypto key nasıl ele alınmalı?

Secret'ı rotate edin, history/build artifacts/logs erişimini inceleyin; yalnızca güncel config'ten silmek yeterli değildir.
