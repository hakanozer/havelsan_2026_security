Broken Authentication

Kimlik doğrulama kullanıcının kim olduğunu kanıtlar; yetkilendirme o kimliğin ne yapabileceğini belirler. Parolanın güvenli saklanması, doğrulama akışının tutarlı olması, brute-force sınırları ve taşıma güvenliği birlikte çalışmalıdır. Projede HTTP Basic ve BCrypt encoder var; özel login endpoint'i ise hash saklama biçimiyle uyumsuz ham parola arıyor.

Neden önemli?

Authentication zayıfsa saldırgan tahmin edilebilir/parola tekrar kullanılan hesapları ele geçirebilir; doğrulama mantığındaki tutarsızlık doğru kullanıcıyı reddedebilir veya yanlış durumu başarılı gösterebilir. Ele geçen kimlikle saldırgan, o kullanıcının sahip olduğu tüm erişimlere kavuşur. Kritik sistemlerde paylaşılan servis hesabı ya da operatör hesabı etkisi, tek bir API'den geniş olabilir.

Basic Authentication parolayı her istekte tekrar taşır; yalnızca TLS üzerinden ve uygun secret yönetimiyle kullanılmalıdır. BCrypt/Argon2 gibi password hashing fonksiyonları çevrimsel maliyetle offline tahmin saldırısını yavaşlatır; düz SHA-256 bu amaçla tasarlanmamıştır.

Saldırı nasıl çalışır?

  1. Saldırgan public login veya HTTP Basic korumalı kaynağa tekrarlı credential dener.
  2. Uygulama parolayı düz saklar, hash'i yanlış kıyaslar, başarısızlıkları sınırlamaz veya hesabın durumunu sızdırır.
  3. Tahmin edilen/tekrar kullanılan parola hesabı açar ya da kullanıcı gerçek parolasıyla giriş yapamaz.
  4. Ele geçen kimlik yetkili endpoint'e taşınır; veri erişimi veya işlem riski doğar.
  5. Yavaş hash, MFA (uygunsa), genel hata yanıtı, per-account/IP rate control, audit ve TLS saldırı maliyetini azaltır.

ÖNCE (projede mevcut: hash saklama ile uyumsuz login)

Bu gerçek kod SQL Injection için parametrik olsa da BCrypt hash saklayan kayıt akışıyla uyumlu kimlik doğrulaması yapmıyor. SQLi ve authentication hatasını ayırın.

Kaynak: src/main/java/com/works/service/CustomerService.java:66-76

public boolean login(CustomerLoginRequestDto req) {    try {        String sql = "select * from customer where email = ? and password = ?";        PreparedStatement st = dataSource.getConnection().prepareStatement(sql);        st.setString(1, req.getEmail());        st.setString(2, req.getPassword());        ResultSet rs = st.executeQuery();        return rs.next();    }catch (Exception e) {        return false;    }}

Parola alanındaki bind parametresi SQL injection'ı engeller; fakat hash karşılaştırması yapmaz. Catch-all exception'ı `false` şekline çevirerek hata nedenini gizleyebilir. Kayıt sırasında parola BCrypt ile encode edilir.

SONRA (Önerilen Düzeltme)

Bu güvenli sürüm projede mevcut değildir. Projedeki repository ve encoder kullanılarak doğrulama ilkesi:

Optional<Customer> found = customerRepository.findByEmailEqualsIgnoreCase(req.getEmail());return found.isPresent()        && passwordEncoder.matches(req.getPassword(), found.get().getPassword());

Uygulamada özel login'ı korumak zorunlu değilse, Spring Security'nin `AuthenticationManager`/filter akışını kullanın; bir doğrulama yolunu tek kaynak yapın. Bu snippet parola hash'i dışarı çıkarmaz; yine de hata mesajları ve rate limit ayrıca tasarlanmalıdır.

Kaba kuvvet önleme yaklaşımı

Projede bir limiter bean'i dakikada 5 istek hakkı ayarlar; `FilterConfig` her istekte aynı bean'i çağırıyor. Kullanıcı/IP/endpoint bazlı anahtar görünmediği için bu, tek başına hesap bazlı brute-force savunması değildir; bir kullanıcının trafiği diğer kullanıcıların hakkını da tüketebilir.

  • Per-account ve IP/cihaz sinyallerini dengeleyin; IP-only kural NAT arkasındaki kullanıcıları etkileyebilir.
  • Progressive delay/backoff uygulayın, ama saldırganın hesabı kilitleyerek hizmet engellemesine yol açmamasını sağlayın.
  • Başarısız girişlerde kullanıcı var/yok bilgisini ayırt etmeyen genel yanıt kullanın.
  • Parola reset ve MFA akışlarına da rate limit/audit ekleyin.
  • Dağıtık servislerde ortak store/gateway limiti; sadece process içi sayaçtan daha tutarlı olur.

Algoritma seçimi kapasite ve risk gereksinimine bağlıdır: sabit pencere, token bucket veya kademeli gecikme. Eşikler gerçek trafikle ve lockout DoS riskiyle test edilmelidir.

Önlemler mimaride nereye oturur?

Credential doğrulama Spring Security/authentication service'te; password hashing kullanıcı kaydı ve verifier'da; abuse kontrolü filter/gateway'de; MFA identity provider veya hassas işlem katmanında; TLS altyapı ve reverse proxy'de durur. Tek başına BCrypt, phishing/reuse/brute-force veya authorization'ı çözmez.

Digest yerine seçimde modern TLS üstünde uygun kimlik protokolü; Form'da CSRF/session; Basic'te TLS ve güvenli credential yönetimi temel gerekliliktir. Savunma, saklama biçimi + rate control + MFA riski + izleme katmanlarının beraber tasarlanmasıdır.

C++ Karşılığı
• C++ HTTP servisinde authentication middleware giriş kimliğini doğrular; her route ayrıca authorization yapar.
• Parolaları düz metin veya hızlı SHA-256 ile saklamayın; uygun Argon2id/BCrypt kütüphanesi kullanın.
• TLS zorunlu tutun; Basic credential'ı açık HTTP üzerinden taşımayın.
• Per-account/IP rate limit ve genel hata yanıtı brute-force ve enumeration riskini azaltır.
• MFA/credential akışında token/secret'ı loglamayın; RAII ile secret buffer yaşam süresini daraltın.
• C++ web framework seçimine göre API'yi doğrulayın; burada kütüphane fonksiyonu varsayılmıyor.

Sık yapılan hatalar ve kontrol listesi

  • Hash kaydedip login'de ham parola eşitliği yapmak.
  • Authentication geçince tüm endpoint'lere erişim vermek.
  • CSRF/session davranışını düşünmeden Form login açmak.
  • Basic'i TLS olmadan kullanmak veya credential'ı loglamak.
  • Tek global rate limiter'ı hesap bazlı brute-force savunması saymak.
  • Kalıcı lockout ile hesap DoS riski yaratmak.
  • Hata yanıtından hesabın var olup olmadığını sızdırmak.
  • Demo kullanıcı/parolasını kaynak koduna/HTML'e yazmak.

Mini sorular

1. BCrypt ile hash edilmiş parola girişte nasıl doğrulanır?

Girilen plaintext ile saklanan hash `PasswordEncoder.matches(raw, encoded)` üzerinden karşılaştırılır; hash çözülerek elde edilmez.

2. Projedeki 5/dakika limiter her hesap için ayrı mıdır?

Kaynakta aynı RateLimiter bean her istekte çağrılır ve kullanıcı/IP anahtarı görünmez; per-account limit olduğu söylenemez.

3. Form login açmak CSRF tasarımını nasıl etkiler?

Tarayıcı session cookie'sini otomatik gönderir; state-changing istekler için CSRF koruması ve cookie/session güvenliği birlikte değerlendirilmelidir.
