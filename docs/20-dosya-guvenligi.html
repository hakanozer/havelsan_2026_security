Path boundary · CWE-22 / CWE-59

Dosya Güvenliği: Path Traversal, izinler ve temp dosyalar

Path Traversal, kullanıcının seçtiği yolun uygulamanın izin verilen dizininden çıkıp başka dosyaya erişmesine neden olur. Tahmin edilebilir temp isimleri/symlink'ler ve geniş file permissions bu etkiyi artırır. Projede REST dosya okuma/yazma/upload endpoint'i görünmüyor; H2 file DB ve log dosyaları uygulama tarafından yönetiliyor, ancak bu doğrudan path traversal endpoint'i değildir.

Neden önemli?

Filename/path request'ten doğrudan `resolve/open/delete` fonksiyonuna giderse separator ve canonical form uygulamanın seçtiği root'u aşabilir. Sonuçta hassas dosya okunabilir, üzerine yazılabilir veya silinebilir. Geniş process permissions etki alanını büyütür; tahmin edilebilir temp file symlink/TOCTOU riskini artırabilir.

Path'i normalize etmek tek başına symlink/TOCTOU yarışlarını çözmez. En güvenli API çoğunlukla kullanıcıdan path değil, server-side authorized file ID almaktır.

Saldırı nasıl çalışır?

  1. İstemci dosya adı veya path segmenti gönderir.
  2. Uygulama bunu trusted base directory ile birleştirip yalnızca string prefix ya da `..` blacklist kontrolü yapar.
  3. Encoded separator, alternate path form veya symlink kontrol sınırını aşar.
  4. File read/write/delete root dışındaki bir hedefe ulaşır.
  5. Canonical base resolution, child path containment, random internal ID, non-symlink storage ve least privilege riski azaltır.

Projemizde nerede?

Path input alan controller, `java.nio.file.Files` kullanım noktası veya file download/delete endpoint'i görünmüyor. H2 file database path'i application.properties:7-8; log output directory logback-spring.xml:4-5, 21-23 olarak configuration ile belirlenmiş; bunlar kullanıcı-controlled file paths değildir.

Dosya yükleme konusunda da mevcut endpoint yok; ayrı 09 · Dosya yükleme güvenliği sayfasına bakın.

ÖNCE / SONRA: proje dosya erişim endpoint'i içermiyor

ÖNCE: Path traversal'a açık bir request-driven file operation alıntısı yok; uydurma project snippet verilmemiştir.

SONRA (Önerilen Düzeltme): User-supplied path yerine server-side file ID ile metadata bulun; root'u canonicalize edin ve resolved child'ın root içinde kaldığını doğrulayın. Örnek JDK yaklaşımı:

Path root = configuredRoot.toRealPath();Path candidate = root.resolve(serverGeneratedName).normalize();if (!candidate.startsWith(root)) rejectRequest();// Open safely; verify symlink/TOCTOU policy for the platform.

Snippet öneridir, proje class/metodu değildir. String `startsWith` path containment için kullanılmamalıdır; `Path.startsWith` path-aware karşılaştırmadır. Symlink ve open-time race politikası ayrıca ele alınır.

File permissions, temporary files ve güvenli silme

  • Process'e yalnızca gereken root ve read/write izinlerini verin.
  • Dosyaları webroot'tan ve executable dizinlerden ayrı saklayın.
  • Temporary file için platformun secure temp creation API'si, random name ve restrictive permissions kullanın.
  • Symlink ve TOCTOU riski varsa check-then-open yerine mümkünse handle/directory-relative safe open pattern kullanın; OS API'si platforma göre doğrulanmalı.
  • Secure deletion SSD/CoW/journaled filesystem üzerinde garanti edilemeyebilir; encryption-at-rest ve key destruction policy'si daha uygun olabilir.
  • Retention, backup ve temp cleanup lifecycle'ını belirleyin.

Önlem mimaride nereye oturur?

Controller file ID contract'ını; service authorization/owner check'i; storage adapter root/path/permission yönetimini; OS/container file permissions etkisini belirler. Upload validation ile download path protection ayrı risklerdir. File ID tahmin edilemez olsa da authorization gereklidir.

C++ Karşılığı
• C++ dosya API'sinde user path'ini root ile raw string birleştirmeyin.
• `std::filesystem` ile canonical path/parent containment kontrolü yapın; symlink/TOCTOU'yu ayrıca ele alın.
• Server-generated file ID/name kullanın; upload original filename'i internal path yapmayın.
• Least privilege, restrictive permissions ve webroot dışı storage uygulayın.
• Temporary file'ları RAII ile temizleyin; secure deletion guarantees'ini filesystem'e göre değerlendirin.
• C++ Core Guidelines/CERT file handling önerilerini review edin.

Sık yapılan hatalar ve kontrol listesi

  • `..` metnini blacklist edip path'i güvenli saymak.
  • Path'i string prefix ile root altında doğrulamak.
  • Symlink veya yarış koşulunu düşünmemek.
  • User filename'ini internal path/temporary file adı yapmak.
  • Dosyayı webroot altında execute edilebilir izinle tutmak.
  • File ID'yi authorization yerine koymak.
  • Secure delete'in her storage üzerinde garantili olduğunu iddia etmek.

Mini sorular

1. `normalize()` sonrası path kesinlikle root altında mıdır?

Hayır. Parent traversal normalizasyonunu çözer; symlink, real path ve TOCTOU ayrıca değerlendirilmelidir.

2. Opaque UUID file ID authorization yerine geçer mi?

Hayır. Tahmin etmeyi zorlaştırır ama bulunan ID için owner/tenant policy yine kontrol edilir.

3. Projede hangi dosya download endpoint'i var?

Envanterde yok. Öneri `FileAccessDemoController` ve `/demo/files/{fileId}`; eklenmeden çalışmaz.
