JCA primitives · key management is part of the design

Java Kriptografi

Kriptografi doğru primitive, anahtar ve kullanım biçimiyle güvenlik sağlar; yanlış anahtar yönetimi güçlü algoritmayı etkisizleştirir. Projede AES/GCM/NoPadding, SecureRandom ile IV, HMAC-SHA256 ve ayrıca BCrypt password encoder var. AES/HMAC anahtar değerleri properties dosyasında bulunduğundan burada paylaşılmıyor.

Neden önemli?

Kripto hatası sırları açığa çıkarabilir veya veri bütünlüğü doğrulanmadan kabul edilmesine yol açabilir. AES-GCM hem gizlilik hem authentication tag sağlar; IV reuse, zayıf key veya key leak olursa garantiler bozulur. Parola saklama farklı bir problemdir: hızlı genel hash parola tahminini yeterince yavaşlatmaz.

Kritik ortamlarda key generation, storage, access policy, rotation, backup ve audit algoritma seçimi kadar önemlidir. Kendi şifreleme algoritmasını yazmayın; Java Cryptography Architecture (JCA) ve doğrulanmış library primitive'lerini kullanın.

Saldırı nasıl çalışır?

  1. Uygulama key'i kod/config içine sabitler veya aynı key'i farklı amaçlarda kullanır.
  2. Key source repository/artifact/log üzerinden açığa çıkar ya da IV/nonce tekrarlanır.
  3. Saldırgan ciphertext'i okuyabilir/değiştirebilir veya parola hash'lerini offline tahmine alabilir.
  4. Yanlış primitive veya kontrolsüz exception veri doğrulamasını da bozabilir.
  5. Purpose-specific key, authenticated encryption, password KDF, SecureRandom ve external key lifecycle risk zincirini azaltır.

ÖNCE (projede mevcut: AES-GCM + random IV)

Gerçek kod AES/GCM/NoPadding, 12-byte IV ve 128-bit tag kullanıyor. IV her encrypt işleminde SecureRandom ile üretiliyor ve ciphertext ile birlikte Base64 çıktısına ekleniyor.

Kaynak: src/main/java/com/works/service/CryptoService.java:27-60

private static final int IV_LENGTH = 12;private static final int TAG_LENGTH = 128;byte[] iv = new byte[IV_LENGTH];new SecureRandom().nextBytes(iv);Cipher cipher = Cipher.getInstance("AES/GCM/NoPadding");new GCMParameterSpec(TAG_LENGTH, iv)ByteBuffer buffer = ByteBuffer.allocate(iv.length + encrypted.length);buffer.put(iv);buffer.put(encrypted);

Artısı: GCM authentication tag üretir, random IV ciphertext ile saklanır. Risk/inceleme: Key'ler source properties'te; key rotation/secret store yok. Same key ile nonce uniqueness operasyonel olarak garanti edilmeli. Broad catch RuntimeException olarak sarılır; endpoint'e giden hata yönetimi açıkça tasarlanmalı.

SONRA (Önerilen Düzeltme)

Kripto primitive kodu tamamen atılmak zorunda değil; key management'i düzeltin, input-format check ve test ekleyin, error handling'i kontrollü yapın. Bu öneri snippet'i key material'ı secret store'dan almayı gösterir, gerçek provider API'si projede yok:

SecretKey key = keyProvider.currentKey("data-encryption");byte[] nonce = secureRandomNonce(12);Cipher cipher = Cipher.getInstance("AES/GCM/NoPadding");// Persist key version + nonce + authenticated ciphertext.

Öneri fonksiyon adları pseudo-code'dur; proje sınıfı değildir. AES-GCM nonce tekrarını önleme ve key-version/rotation tasarımı sistem ölçeğinde doğrulanmalıdır.

Hash + salt, BCrypt/Argon2 ve hassas parametreler

  • Parolayı encrypt edip geri çözmek yerine adaptive password hashing kullanın.
  • BCrypt/Argon2 salt'i password hash formatında yönetir; genel SHA-256 hızlıdır ve parola saklamaya uygun değildir.
  • Work factor'ı uygulama kapasitesi ve login latency budget'ına göre benchmark edin; migration/rehash stratejisi planlayın.
  • SecureRandom security token/IV üretiminde kullanılır; `java.util.Random` güvenlik sırrı için kullanılmamalı.
  • Hassas parametreleri request/exception loglarına koymayın; projedeki filter SessionId logluyor, password loglamıyor.
  • AES encryption, password hashing'in alternatifi değildir; HMAC integrity/authentication içindir ve key management gerektirir.

Önlem mimaride nereye oturur?

Cryptographic service primitive'i; config/secret manager key lifecycle'ı; API/controller hata davranışı ve input limitlerini; deployment IAM key erişimini uygular. Encryption key, MAC key ve password hash parametreleri amaçlarına göre ayrılmalıdır. Algoritmayı doğru seçmek key'i güvenli saklamaz; secret management tasarımın parçasıdır.

C++ Karşılığı
• Kendi encryption/hash algoritmanızı yazmayın; OpenSSL/libsodium gibi doğrulanmış library kullanın.
• AES-GCM gibi AEAD'de nonce reuse ve tag verification'ı doğru yönetin.
• Parola saklamak için password KDF; genel SHA-256 değil, uygun Argon2id/BCrypt library seçin.
• Key'i kaynak koda yazmayın; secret store, rotation ve erişim kontrolü kullanın.
• Random key/nonce için OS-backed cryptographic RNG kullanın.
• Secret material'ı log ve exception'lara yazmayın; RAII ile ömrünü sınırlandırın.

Sık yapılan hatalar ve kontrol listesi

  • Hash, encryption ve HMAC'i aynı amaçta kullanmak.
  • Parolayı hızlı SHA-256 ile saklamak.
  • AES-GCM nonce/IV uniqueness'i garanti etmemek.
  • Anahtarı properties/git'e commit etmek veya rotation planlamamak.
  • Authentication tag doğrulanmadan plaintext kullanmak.
  • Crypto exception'ını detaylı response'a yaymak.
  • Key ve hassas request parametrelerini loglamak.

Mini sorular

1. Parolayı neden AES ile şifrelemek yerine BCrypt/Argon2 ile hash'leriz?

Uygulama parolayı geri elde etmemelidir; adaptive KDF çevrimsel maliyetle tahmin saldırısını yavaşlatır ve salt yönetir.

2. AES-GCM'de IV gizli olmak zorunda mıdır?

IV/nonce genelde ciphertext yanında saklanabilir; aynı key altında tekrar kullanılmaması ve formatta doğru bağlanması kritik.

3. SecureRandom kullanmak hardcoded key sorununu çözer mi?

Hayır. Rastgele IV üretimini destekler; sabit encryption key'in source control'da bulunmasını çözmez.
