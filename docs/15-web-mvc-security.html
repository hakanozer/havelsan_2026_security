Web MVC Security: Filter ve SecurityFilterChain

Servlet Filter request/response MVC controller'a ulaşmadan önce kesitsel kontroller uygular. Spring Security'nin SecurityFilterChain'i authentication, authorization, CSRF ve header politikalarını sıraya koyar. Projede ayrıca `Filter` implementasyonu ile wrapper/rate limit/loglama yapılıyor; `OncePerRequestFilter` veya Security chain'e özel registration görünmüyor.

Neden önemli?

Web MVC katmanında authentication, authorization, CORS, CSRF, input parsing, header ve audit kontrolleri farklı noktalara dağılır. Filter chain yanlış sıralanır, request body tüketilir veya CORS policy fazla açılırsa beklenen güvenlik kontrolü çalışmayabilir. Sonuç isteklerin denetimsiz geçmesi, yanlış hata davranışı veya sensitive request metadata'sının sızması olabilir.

Filter global kontrol için uygundur; iş nesnesi sahipliği/validation gibi controller/service kurallarını filtreye taşıyıp tek katmanda toplamak doğru değildir. SecurityFilterChain ise Spring Security concern'lerini uygulama filter policy'sinde açıkça bağlar.

Saldırı nasıl çalışır?

  1. İstek Servlet container'a gelir ve Filter pipeline'dan geçer.
  2. Güvenlik filtresi authentication/authorization/token/header kararlarını uygular.
  3. Uygulama filter body'yi tüketir/değiştirir veya yanlış sırada çalışırsa MVC converter beklediği veriyi alamaz.
  4. CORS yanlış origin/credential policy ile browser'a istenmeyen cross-origin erişim verebilir; CSRF'yi tek başına çözmez.
  5. Filter registration, ordering, dispatcher davranışı ve SecurityFilterChain integration test edilir.

  • Servlet `Filter` implementasyonu: FilterConfig.java:16-70.

Projede `OncePerRequestFilter`, explicit `FilterRegistrationBean`, custom SecurityFilterChain filter insertion, explicit security headers config görünmüyor. Servlet container filter order/runtime behavior ayrıca doğrulanmalı.

SONRA (Önerilen Düzeltme)

Her concern için doğru extension point kullanın: authentication/authorization/CSRF/header politikası SecurityFilterChain; application-specific request metadata/trace uygun Servlet Filter veya OncePerRequestFilter. Projede `OncePerRequestFilter` yoktur. Aşağıdaki filtre zinciri açıklama amaçlıdır, ekli kod değildir.

SecurityFilterChain: authentication → authorization → CSRF/headersOncePerRequestFilter: correlation/audit concern (body rewrite gerekmedikçe)Controller/DTO: request binding + Bean ValidationService: business authorization and ownership policy

Spring Security 6/7 API'deki değişiklikleri Boot 4.1.0 dependency management ile doğrulayın; `WebSecurityConfigurerAdapter` eski yöntemdir ve bu projede kullanılmıyor.

Canlı demo adımları

  1. `GET /product/list` isteğini anonymous gönderip SecurityFilterChain davranışını gözlemleyin. DB seed/authority yoksa erişim kararını source config ve runtime response ile doğrulayın.
  2. Filter'daki rate limiter nedeniyle 1 dakikada 5 istek eşiğini aşmayacak şekilde local test edin; limiter global olabilir.
  3. Browser devtools ile CORS preflight/response header'larını iki configured origin için inceleyin. CORS wildcard değil fakat credentials açık.
  4. Filter'ın `getSession` ve body wrapper etkisini küçük JSON request ile gözleyin; aynı body controller'a ulaşıyor mu test edin.
  5. Security headers/CSP gibi header'ların uygulama veya proxy tarafından gelip gelmediğini response'ta ölçün; source config'te yokluğu runtime'da kesin yokluk demek değildir.

Security headers ve CORS

  • Security headers için X-Content-Type-Options, frame policy, Referrer-Policy ve CSP'yi uygulama/proxy katmanında belirleyin; ihtiyaca göre test edin.
  • CORS allowed origins listesi dar olmalı. Projede `allowCredentials(true)` ile iki açık origin tanımlı; origin/credential kullanımını business modelle doğrulayın.
  • Allowed headers `*` ise browser preflight davranışını ve custom auth header gereksinimini doğrulayın.
  • CORS browser erişim politikasıdır; authentication, authorization veya CSRF defense değildir.
  • Filter ordering ve dispatcher types; async/error/forward dispatch davranışları üzerinde integration test ile doğrulanmalı.
  • Request body'yi global sanitize etmek yerine DTO validation/output context kontrollerini seçin.

Önlem mimaride nereye oturur?

Servlet container genel pipeline'ı; SecurityFilterChain authentication/authorization/CSRF/security headers; MVC binding ve Bean Validation; service object-level policy; reverse proxy TLS/rate/edge header katmanını kapsar. Defense in depth için aynı policy'yi farklı endpoint'te bypass etmeyecek entegrasyon testleri yazılır.

C++ Karşılığı
• C++ web server middleware/filter zinciri request routing'den önce ortak kontroller uygular.
• Authn/authz, CORS, CSRF ve headers'i tek global string sanitizer'a yüklemeyin.
• Middleware sırasını ve error/async path'lerini entegrasyon testleriyle doğrulayın.

Sık yapılan hatalar ve kontrol listesi

  • Generic Servlet Filter'ı Spring Security chain'ine kayıtlı sanmak.
  • OncePerRequestFilter'ın her dispatch/type için otomatik tek kez çalışacağını varsaymak.
  • Filter içinde body'yi limitsiz okuyup tekrar oluşturmak.
  • CORS'u authorization veya CSRF önlemi saymak.
  • `allowCredentials(true)` ile geniş origin'leri onaylamak.
  • Headers'i security config'te ayarlayıp proxy'nin overwrite etmesini fark etmemek.
  • Uygulama testinde gerçek filter order/exception path'i kapsamamak.

Mini sorular

1. `OncePerRequestFilter` projede kullanılıyor mu?

Hayır. Mevcut `FilterConfig` `jakarta.servlet.Filter` implement ediyor.

2. CORS ile CSRF arasındaki fark nedir?

CORS browser'ın cross-origin response erişim davranışını; CSRF ise ambient credentials ile state-changing request'in niyet doğrulamasını ele alır.

3. SecurityFilterChain controller validation yerine geçer mi?

Hayır. Filter chain request güvenlik politikası uygular; DTO/Controller validation input contract'ını ve service iş kuralları domain'i korur.
