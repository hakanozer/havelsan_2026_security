Role-based access control · OWASP A01

Basic Authentication ve Roller

Basic Authentication credential doğrulama biçimidir; rol, doğrulanmış identity'nin hangi işleme erişebileceğini belirler. Bu projede HTTP Basic, CustomerService role loading ve product/note path rules var. `hasRole("product")` ile DB authority adının prefix uyumu ve public registration'daki role ataması runtime/contract test ile doğrulanmalıdır.

Neden önemli?

Authentication kullanıcıyı tanımlar, role-based authorization fonksiyon erişimini kısıtlar. Role check eksik veya authority adı yanlış eşlenmişse ya erişim reddedilir ya da yanlış kullanıcıya izin verilir. Kritik sistemlerde function-level role ile object/tenant-level authorization birlikte uygulanmalıdır.

Basic credentials her request'te taşındığı için TLS gerekir. Role yönetimi istemci DTO'suna bırakılamaz; server-side provisioning ve least privilege uygulanmalıdır.

Saldırı nasıl çalışır?

  1. Kullanıcı Basic credential ile authentication yapar.
  2. SecurityFilterChain path'i role ile eşler.
  3. Authority adları yanlış prefix/case ile yüklenirse policy beklenenden farklı sonuç verir.
  4. Public registration'da client role gönderebiliyorsa role assignment trust boundary'si oluşur.
  5. Role mapping'i standardize edin, client'tan permission almayın, function/object authorization test edin.

Projemizde nerede?

  • Basic + endpoint role rules + provider: SecurityConfig.java:22-42.
  • DB role names authority'ye çevriliyor: CustomerService.java:45-64.
  • Registration DTO roles kabul ediyor: CustomerRegisterRequestDto.java:26-28; servis map ediyor CustomerService.java:38-42.
  • Yorumlanan örnek kullanıcı/roller: SecurityConfig.java:45-48; seed/parola kodu değil.

ÖNCE (projede mevcut role mapping)

Security DSL `hasRole("product")` ve `hasRole("note")` kullanıyor. Spring Security'nin standart `hasRole` davranışı role prefix ekler; CustomerService ise DB role name'ini olduğu gibi `GrantedAuthority` olarak döndürür. Yorumda prefixsiz adlar verilmiş. Gerçek DB authority değerleri standard `ROLE_` prefix'i içeriyor mu doğrulanmalıdır; aksi halde yetkili kullanıcı da reddedilebilir.

Kaynak: SecurityConfig.java:25-34 ve CustomerService.java:58-63.

.httpBasic(Customizer.withDefaults()).authorizeHttpRequests(req ->    req.requestMatchers("/product/**").hasRole("product")       .requestMatchers("/note/**").hasRole("note")       .requestMatchers("/customer/**").permitAll()authorities.add(() -> role.getName());

SONRA (Önerilen Düzeltme)

İki güvenli tasarımdan birini tutarlı seçin. DB role values standard `ROLE_PRODUCT` ise `hasRole("PRODUCT")` gibi normalize edilmiş standard kullanın; DB values literal `product` ise explicit `hasAuthority("product")` ile exact authority kullanın. Public register DTO'dan role alanını çıkarıp server-side default role atayın. Aşağıdaki bir alternatif öneridir, proje alıntısı değildir:

.requestMatchers("/product/**").hasAuthority("product").requestMatchers("/note/**").hasAuthority("note")// User role assignment is server-managed, not request-provided.

Role-based ve method security

  • URL matcher API route groups için merkezi sınır koyar.
  • Method security iş metodu seviyesinde guard sağlayabilir; projede `@PreAuthorize`/`@EnableMethodSecurity` görünmüyor.
  • Role coarse-grained yetkidir; user/object ownership, tenant scoping ve transaction-level rules ayrı kontrol edilir.
  • Authentication principal/authority client request body'den güvenilmez.
  • “Admin” role'ü gereksiz yere genişletmeyin; separation of duties ve audit uygulanmalı.

Neden sadece UI button gizlemek değil? Kullanıcı endpoint'i doğrudan çağırabilir; backend policy her request'te uygulanmalıdır. Neden sadece URL role değil? Service farklı route/async path üzerinden çağrıldığında iş kuralı service method'unda korunabilir.

Canlı demo adımları

  1. Local DB'de known role names ve `CustomerService.loadUserByUsername` authority output'unu kontrol edin.
  2. SecurityConfig'teki `hasRole` prefix davranışını test edin; `ROLE_` ad uyumunu doğrulayın. Gerçek credentials repoda yok.
  3. Product-role hesabıyla `GET /product/list`, note-only hesabıyla product endpoint'i ve tersini deneyin. Beklenen izin/ret DB rollerine bağlıdır; test hesabı yoksa 00-proje-tanitimi sayfasındaki uyarıyı izleyin.
  4. CSRF/HTTP transport etkisini ayırın: Basic auth için HTTPS gereklidir; CSRF sayfasındaki browser credential modelini dikkate alın.
  5. Public registration roles alanını inceleyin; düşük ayrıcalıklı default role'ü server-side atama önerisini tartışın.

Önlem mimaride nereye oturur?

Authentication provider principal üretir; SecurityFilterChain function-level role'ü; method security service işlevini; repository query ownership/tenant kapsamını uygular. Role assignment yönetim/registration service'inde server-side kalır. Her katmanda aynı role vocabulary kullanılmalı ve deny testleri bulunmalıdır.

C++ Karşılığı
• HTTP Basic identity doğrular; HTTPS zorunlu ve her endpoint için authorization ayrıca uygulanır.
• Role/permission enum veya trusted directory'den gelir; request body'den yetki atamayın.
• Function-level permission ile object ownership/tenant query scope'u birleştirin.
• Deny-by-default ve negatif role testleri endpoint/service düzeyinde çalışsın.
• Credential, role claim veya principal'ı loglarda minimize edin.
• Framework middleware API'sini kullanılan C++ server sürümünde doğrulayın.

Sık yapılan hatalar ve kontrol listesi

  • `hasRole` prefix ile GrantedAuthority formatını uyumsuz bırakmak.
  • Role isimlerinde case/prefix standardı tanımlamamak.
  • Public signup'ta client'tan role/permission almak.
  • Basic authentication'ı HTTP üzerinde kullanmak.
  • Role check'i UI'da yapıp backend'de atlamak.
  • Role check'in object ownership'i de koruduğunu varsaymak.
  • Eksik seed verisi nedeniyle 401/403 davranışını yanlış yorumlamak.

Mini sorular

1. Spring `hasRole("product")` hangi authority ile eşleşme açısından kontrol edilmelidir?

Standart role prefix davranışı nedeniyle DB authority name'in `ROLE_product` olup olmadığı ve custom prefix bulunup bulunmadığı doğrulanmalıdır.

2. User'ın request body'de role göndermesi neden sakıncalı?

İstemci kendi yetkisini belirleyemez; role assignment trusted server-side policy ile yapılmalıdır.

3. Role check BOLA'yı engellemek için yeterli mi?

Hayır. İstenen nesnenin owner/tenant ilişkisi de her işlemde doğrulanmalıdır.
