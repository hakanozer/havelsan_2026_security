Browser output context · OWASP A03:2021

XSS ve Anti-XSS Output Encoding

Cross-Site Scripting (XSS), güvenilmeyen veri browser'da çalıştırılabilir HTML/JavaScript bağlamında güvenli encode edilmeden gösterildiğinde oluşur. Request sanitization tek başına XSS koruması değildir; çıktı bağlamında encoding ve güvenli DOM sink'i gerekir. Projede global request wrapper var, fakat HTML response render eden UI/sink görünmüyor; bu nedenle exploit doğrulanmış sayılmaz.

Neden önemli?

Persistent XSS'te kaydedilmiş metin sonraki kullanıcıya; reflected XSS'te request-derived text response'a; DOM XSS'te client-side script tehlikeli DOM sink'ine ulaşır. Browser kodu sayfanın origin'i altında çalıştığından UI içeriği, kullanıcı etkileşimi veya session'a erişim etkilenebilir. `HttpOnly` token okumasını sınırlar ancak XSS'i ortadan kaldırmaz.

Kritik/kurumsal web arayüzlerinde çıktı güvenliği veri kaynağına değil, verinin kullanıldığı HTML/attribute/URL/JavaScript bağlamına göre belirlenir. OWASP XSS Prevention Cheat Sheet ve CWE-79 rehber olarak kullanılabilir.

Saldırı nasıl çalışır?

  1. Kullanıcı-controlled text (ör. Note content) API'ye girer ve saklanır/response'ta döner.
  2. Frontend metni raw HTML sink'ine veya unsafe template interpolation'a koyar.
  3. Browser metni içerik yerine markup/script olarak yorumlar.
  4. Script sayfa origin'inde çalışır; gösterilen UI veya kullanıcı etkileşimini kötüye kullanabilir.
  5. Context-specific output encoding, autoescaped template, `textContent` gibi text sink ve CSP defense-in-depth zinciri keser.

Projemizde nerede?

  • Filter wrapper uygulanması: FilterConfig.java:28-34, 69.
  • Sanitizer: XssRequestWrapper.java:13-60.

Proje kaynaklarında HTML renderer/browser frontend yok. `Note` JSON'unu bir frontend raw HTML sink'inde render ederse XSS sink'i oluşabilir; mevcut backend tek başına stored XSS'i kanıtlamaz.

ÖNCE (projede mevcut: request'i genel sanitize etme)

Bu gerçek wrapper request body'sini, parametre ve header'ları genel biçimde Jsoup ile temizler. Bu satırlar “XSS açığı kanıtlandı” değildir; uygulamanın input tarafında global sanitization yaptığını gösterir. Global mutasyon zengin metni bozabilir, encoding farkı doğurabilir ve browser output bağlamını bilmez.

Kaynak: src/main/java/com/works/config/XssRequestWrapper.java:17-21, 58-60

public XssRequestWrapper(HttpServletRequest request) throws IOException {    byte[] raw = request.getInputStream().readAllBytes();    String body = new String(raw);    this.sanitizedBody = sanitize(body).getBytes();private String sanitize(String input) {    return Jsoup.clean(input, Safelist.none());}

Body için `new String(raw)` ve `.getBytes()` platform default charset'e bağlı; JSON body'nin byte/character semantiğini değiştirebilir. Ayrıca Servlet body'yi baştan tüketip wrapper ile tekrar sunmak request parsing davranışını etkileyebilir. Bu, output encoding çözümü değildir.

SONRA (Önerilen Düzeltme): değeri render bağlamında encode et

Projede UI/template olmadığı için gerçek güvenli renderer örneği yok. HTML text node bağlamında Spring'in `HtmlUtils.htmlEscape` gibi doğrulanmış encoder'ını kullanmak bir öneridir; attribute, JavaScript, CSS veya URL bağlamına bunu gelişigüzel taşımayın. Mümkünse framework'ün autoescaped template/text sink'ini tercih edin.

String safeText = HtmlUtils.htmlEscape(untrustedText);// Sadece HTML text context için; raw HTML/JS sink'e koymayın.
DikkatEncoder'ı doğru bağlamda kullanın. JavaScript string'i, URL veya CSS için HTML text encoder'ı tek başına yeterli değildir. Girdi gerçekten HTML kabul edecekse sanitize allowlist policy kullanılır; düz metin için HTML encoding tercih edilir.

Canlı demo adımları

  1. Mevcut endpoint POST /note/save JSON kabul eder ve Note döndürür; bu API response'u browser'da render eden UI projede yoktur.
  2. Yalnızca local test instance'ta title/content alanına zararsız HTML işaretleme metni gönderin. API response'un raw markup içermesi browser'da script çalıştığını kanıtlamaz.
  3. Wrapper sonrası server response/input değerindeki dönüşümü inceleyin; metnin korunması/bozulmasını kaydedin.
  4. İsteğe bağlı demo frontend eklenirse text sink ve raw HTML sink farkını güvenli dummy sayfada karşılaştırın; execution payload'ı yayımlamayın veya gerçek tarayıcı kullanıcı verisi kullanmayın.
  5. Güvenli renderer'da değer görünür literal text olmalı; markup/script olarak yorumlanmamalıdır.

Önlem mimaride nereye oturur?

Input validation kabul edilen iş verisini/formatı doğrular; model veriyi metin olarak saklar; output encoder browser sink'inde bağlama göre escape eder. Güvenilir template autoescaping tercih edilir. Global request sanitizer ise XSS output encoding yerine geçmez; HTML içeriği izinli olacaksa ayrıca dar sanitizer politikası gerekir. CSP, HttpOnly ve Security headers ek savunmadır, temel output encoding'in alternatifi değil.

C++ Karşılığı
• C++ web/HTTP servisinde tainted text'i HTML response'a ham eklemeyin.
• HTML text, attribute, URL ve JavaScript context'leri için doğru encoder/framework template'ini seçin.
• Request'i global değiştirmek yerine veriyi doğrulayın, response sink'inde encode edin.
• Boost.Beast/Crow/Drogon'da template/response API'sini kullanılan sürümde doğrulayın.
• CSP defense-in-depth'tir; output encoding'i ikame etmez.
• XSS testlerini yalnızca local fixture ve inert text ile yapın.

Sık yapılan hatalar ve kontrol listesi

  • Input sanitization'ı output encoding sanmak.
  • Her bağlamda aynı HTML escaping'i kullanmak.
  • API JSON response'unu doğrudan browser execution sanmak.
  • Güvenilmeyen değeri `innerHTML`/raw template'e koymak.
  • Rich text gerekiyorsa allowlist'i tanımlamamak.
  • Content-Security-Policy'yi tek başına çözüm görmek.
  • Request body encoding/stream'ini genel filter ile bozmak.
  • XSS'in kanıtlanmadığı projede açığı var diye kesin iddia etmek.

Mini sorular

1. API'nin `metin` döndürmesi XSS'in kanıtı mıdır?

Hayır. XSS için browser'ın bunu hangi sink'te nasıl yorumladığı incelenmeli; JSON içinde dönmesi tek başına script execution göstermez.

2. Global `Jsoup.clean` output encoding yerine geçer mi?

Hayır. Request'te genel bir dönüşüm yapar; response'taki HTML/attribute/JS bağlamını bilmez.

3. Düz metin browser'da nasıl güvenli gösterilir?

Autoescaped template veya textContent gibi text sink kullanılır; server-rendered HTML'de doğru context encoder uygulanır.
