SQL Injection

SQL Injection, uygulamanın SQL komutunu kullanıcı girdisiyle metin birleştirerek kurması ve veritabanının girdiyi veri yerine komut olarak yorumlamasıyla oluşur. Projedeki login sorgusu parametre bağladığı için bu zafiyetin zayıf örneği değildir. Buradaki asıl ders, güvenli SQL biçimiyle uygulama katmanındaki parola doğrulama tutarsızlığını birbirinden ayırmaktır.

Neden önemli?

SQL komutu veritabanına uygulamanın yetkileriyle gider. Komut ile veri ayrılmadığında, saldırgan filtre koşulunu değiştirebilir veya erişebildiği satırlardaki veriyi okuyup değiştirebilir; kaynak ve sorgu yetkilerine göre servis sürekliliği de etkilenebilir. Kritik sistemlerde bunun sonucu konfigürasyon veya operasyon verisinin gizliliği/bütünlüğü olabilir.

Parametreli sorgu, SQL yapısını sabit tutup kullanıcı girdisini değer olarak bağlar. Blacklist ise yalnızca tanıdığı metakarakterleri arar; farklı encoding/sözdizimi ve kullanım bağlamları nedeniyle temel savunma olarak yeterli değildir.

Saldırı nasıl çalışır?

  1. İstek gövdesinden email gibi bir değer gelir.
  2. Zayıf uygulama değeri `" ... '" + input + "'"` biçiminde SQL metnine ekler.
  3. Veritabanı sorgu parser'ı eklenen özel sözdizimini komutun parçası kabul eder.
  4. Koşul değişir ve sorgu beklenmeyen satır/işlemleri döndürür.
  5. Prepared statement yapıyı önceden ayırır, girdiyi parametre olarak bağlar; veritabanı onu SQL sözdizimi değil değer olarak ele alır.
DikkatBu derste saldırı dizgileri yalnızca yerel test girdisi olarak ve davranışı anlamak için kullanılır. Genişletilmiş istismar zinciri veya gerçek sistem testi kapsam dışıdır.

Projemizde nerede?

  • HTTP girişi: CustomerController.java:26-30 — POST /customer/login.
  • Sorgu ve parametre bağlama: CustomerService.java:66-78.
  • Kayıt parolası BCrypt ile kodlanıyor: CustomerService.java:38-42, encoder bean'i AppBeans.java:17-20.

ÖNCE (projede mevcut, SQLi açısından güvenli)

Zayıf string-concatenation sorgusu projede bulunmuyor. Aşağıdaki gerçek kod, `CustomerService.login` içindeki parametreli akıştır; kırmızı zayıf satır olmadığını özellikle not edin.

Kaynak: src/main/java/com/works/service/CustomerService.java:66-78

public boolean login(CustomerLoginRequestDto req) {    String sql = "select * from customer where email = ? and password = ?";    PreparedStatement st = dataSource.getConnection().prepareStatement(sql);    st.setString(1, req.getEmail());    st.setString(2, req.getPassword());    ResultSet rs = st.executeQuery();    return rs.next();}

Neden güvenli? Sorgu şablonu değişmez; `setString` değerleri parametre olarak bağlar. Bir saldırı dizgisi parametre değeri olur, yeni SQL operatörü veya koşul haline gelmez. İlgili ama farklı hata: Bu metod ham parolayı DB sütunuyla karşılaştırır; kayıt metodu BCrypt hash'i sakladığından normal kayıt kullanıcısının girişi tutarlı çalışmayabilir.

SONRA (önerilen düzeltme: auth akışını tekilleştir)

Projede bu login metodu için güvenli bir ikinci versiyon yok. Öneri kodu, kullanıcının e-postasıyla kaydı bulup BCrypt `matches` ile girilen parolayı karşılaştırma ilkesini gösterir. Kurumsal akışta mümkünse endpoint'i Spring Security authentication mekanizmasına bağlayın; aşağıdaki parça mevcut sınıftan alıntı değildir.

Optional<Customer> found = customerRepository.findByEmailEqualsIgnoreCase(req.getEmail());return found.isPresent()        && passwordEncoder.matches(req.getPassword(), found.get().getPassword());

Bu öneri SQL metni kurmaz; ORM repository lookup'ı ve BCrypt doğrulamasını kullanır. E-posta araması mevcut, kaydı gösterme ve credential saklama detayları ürün gereksinimine göre tamamlanmalıdır.

Canlı demo adımları

  1. DB'de test customer mevcutsa, `POST /customer/login` için doğru e-posta/parolayı gönderin. Kayıt yolu BCrypt hash sakladığından mevcut metodun ham eşlemesi `false` döndürebilir; bu SQLi kanıtı değildir.
  2. Aynı istekte e-posta alanına sıradan bir test dizgesi ve sonra basit `' OR '1'='1` karakter dizisini verin. Parametreli sorgu girdiyi literal değer olarak arar; hedef veri satırının bulunmasına bağlı olarak `false` beklenir.
  3. Sorgu kodunu loglarda/SQL trace'te inceleyin; girdinin sorgu yapısına eklenmediğini teyit edin. `spring.jpa.show-sql` bu JDBC çağrısını nasıl gösteriyor, sürücü logundan ayrıca doğrulanmalıdır.
curl -i -X POST http://localhost:8090/customer/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"'\'' OR '\''1'\''='\''1","password":"demo"}'
# Yanıt uygulamanın mevcut verisine göre true/false olabilir; payload SQL kodu değildir.
Eğitmen NotuGerçek login çıktısı veritabanı seed durumuna bağlıdır. Öğrencilere “false = SQLi engellendi” yerine kaynak kodundaki sabit query ve bind parametrelerini kanıtlatın.

Önlem neden önemli ve nerede durur?

Parametre bağlama veri erişim sınırında, repository/JDBC katmanında uygulanır. Controller'da regex/blacklist yapmak SQLi savunmasının yerine geçmez; izinli iş verisini doğrulamak için yine gereklidir. Parametreler tablo/sütun adları gibi SQL identifier'larını genellikle bağlayamaz; dinamik identifier gerekiyorsa sabit izinli seçeneklerden seçin.

Defense in depth: minimum DB yetkisi, input validation, sabit query şablonu, güvenli hata yönetimi ve sorgu testleri birlikte kullanılır. String concatenation “kaçış karakteri” ekleyerek düzeltmek yerine prepared statement seçilir; escaping'i tüm SQL bağlamlarında doğru yapmak daha kırılgan ve hataya açıktır.

C++ Karşılığı
• SQL'i `"... WHERE name='" + input` ile kurmak SQL Injection üretir.
• SQLite, libpq veya ODBC için prepared statement/bind parametre kullanın.
• Parametreler SQL syntax'ından ayrılır; sadece giriş blacklist'iyle yetinmeyin.
• SQL identifier dinamikse izinli sabit ad eşlemesi kullanın.
• RAII ile statement/connection kaynaklarını güvenli yönetin.
• `clang-tidy`/`cppcheck` incelemesini entegrasyon testleriyle tamamlayın.

Sık yapılan hatalar ve kontrol listesi

  • Bir query'de `?` görmekle tüm akış güvenli sanmak; diğer sorguları da tarayın.
  • PreparedStatement kullanırken yine ham parolayı SQL ile doğrulamak.
  • Input validation'ın prepared statement yerine geçmesini beklemek.
  • DB hesabına uygulamanın ihtiyacından fazla yetki vermek.
  • SQL exception ayrıntısını istemciye döndürmek.
  • Parametrelenemeyen sütun/sıralama alanını doğrudan kullanıcıdan almak.
  • Login davranışı testini DB seed'i ve parola saklama biçiminden bağımsız yorumlamak.

Mini sorular

1. Parametreli sorgu `' OR '1'='1` ifadesini neden SQL koşulu yapmaz?

Query yapısı ve parametre değerleri ayrı gönderilir; veritabanı bunu komut metni değil string değeri olarak işler.

2. SQLi engellendiği halde login neden false dönebilir?

Projede kayıt akışı BCrypt hash saklıyor; mevcut test login'i ham parolayı sütunla eşitlik üzerinden arıyor. Bu ayrı bir authentication uyumsuzluğudur.

3. Sadece email için regex eklemek yeterli mi?

Hayır. Regex iş kuralı doğrular; SQL query'nin parametrelenmesinin alternatifi değildir.
