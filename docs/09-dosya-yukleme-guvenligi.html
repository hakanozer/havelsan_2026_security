Dosya Yükleme Güvenliği

Arbitrary File Upload, istemcinin gönderdiği dosyanın türü/içeriği/yolu denetlenmeden saklanıp işlenmesiyle oluşur. Dosya adı, uzantı veya `Content-Type` tek başına gerçek içeriği kanıtlamaz. Bu projede multipart upload endpoint'i yok; bu nedenle sayfa gerçek kod örneği uydurmaz, güvenli demo tasarımını önerir.

Neden önemli?

Dosya public web root'ta veya çalıştırılabilir dizinde saklanırsa, doğrulanmamış dosya active content olarak sunulabilir; path seçimi hatalıysa dosya üzerine yazma veya servis dışı kalma riski doğar. Büyük/decompression bomb dosyaları CPU, bellek ve disk tüketebilir. Kritik uygulamalarda yüklenen belge/çizim/telemetri dosyalarının bütünlüğü ve zararlı içerik taraması tedarik zinciri sınırıdır.

Dosya kabulünü uzantı blacklist'iyle çözmek yeterli değildir: MIME başlığı ve dosya adı saldırgan tarafından seçilebilir, polyglot içerikler birden çok parser'ı etkileyebilir. Allowlist, boyut sınırı, içerik tanıma, yeniden işleme ve güvenli storage birlikte kullanılır.

Saldırı nasıl çalışır?

  1. İstemci dosyayı ve filename/content-type metadata'sını gönderir.
  2. Sunucu yalnızca uzantıya veya header'a güvenir; path veya boyut kontrolü yapmaz.
  3. Dosya uygulama/web köküne ya da tahmin edilebilir isimle yazılır.
  4. Dosya daha sonra server/browser parser tarafından çalıştırılır, parse edilir, üzerine yazar veya kaynak tüketir.
  5. Allowlisted format, byte-level içerik doğrulama, boyut/işlem sınırı, random server-side isim ve web-root dışı storage riski düşürür.

Projemizde nerede?

Gerçek upload controller veya Multipart dependency/endpoint bulunmadı; mevcut controller listesi ProductController, NoteController, CustomerController ile sınırlı. Projede upload akışı yoktur.

ÖNCE / SONRA: projede upload kodu yok

ÖNCE (zayıf proje kodu): Dosya alan endpoint/sınıf olmadığı için zayıf alıntı yok. Uydurma kodu proje alıntısı gibi göstermiyoruz.

SONRA (Önerilen Düzeltme): Demo eklenirse uçtan uca doğrulama zinciri: auth/authorization → request size limit → allowlist → dosya signature/decoder doğrulaması → random internal identifier → webroot dışı storage → malware scan/quarantine ve kontrollü download response. Client-supplied filename storage path'ine doğrudan eklenmemelidir.

Minimum demo önerisi
  • Paket: com.works.demo.
  • Sınıf: FileUploadDemoController (proje kaynaklarında yok).
  • Endpoint: POST /demo/files (öneri, mevcut değil).
  • Yalnızca izole local profile; küçük allowlisted PNG/JPEG fixture; web root dışındaki geçici klasör; sabit boyut limiti; server-side random isim.
  • Dosyayı direct execution/content rendering yerine güvenli download response ile sunun; deneme sonrası temp dosyaları temizleyin.

Canlı demo adımları · önerilen endpoint

  1. Önce doğrulanmış sample image ile accepted path'i test edin; response sadece server-generated identifier döndürsün.
  2. Uzantı ve MIME header'ı uyumsuz olan test fixture verin; server-side signature/decoder doğrulaması reddetmeli.
  3. Aşırı boyutlu test dosyasını göndermeden önce server limitini belirleyin; servis dosyayı belleğe limitsiz almadan reddetmeli.
  4. Filename içinde path separator veya traversal benzeri basit test metni varsa storage path'i kullanıcı adından türememeli; yalnızca kendi temp dizininizde doğrulayın.
  5. Her testten sonra temp upload/artifact temizliğini doğrulayın. Gerçek endpoint olmadığı için bu adımlar eklenmeden çalışmaz.
# ÖNERİLEN endpoint; proje şu anda bunu sunmuyor:
curl -i -X POST http://localhost:8090/demo/files \
  -F 'file=@./sample.png;type=image/png'
DikkatEndpoint önerisi kopyalanıp mevcut API'ye gönderilemez. Demo implement edilmeden file upload isteği beklenemez; internetten indirilen veya gerçek belge içeren dosyalarla eğitim yapmayın.

Image dosyalarını güvenli yükleme

  • Format allowlist'i dar tutun; filename uzantısı ve `Content-Type` header'ını tek başına güvenme sinyali saymayın.
  • Image decoder ile içeriği parse edin; en-boy, pixel count ve decode time limitleri koyun.
  • Mümkünse görüntüyü decode edip yeniden encode ederek metadata/ek içerik riskini azaltın; metadata gerekiyorsa açıkça seçin.
  • SVG aktif XML/HTML içerik taşıyabilir; raster image ile aynı güven modelinde değerlendirmeyin.
  • Storage webroot dışına; private ve non-executable izinlerle yapılmalı, download sırasında doğru `Content-Type` ve `Content-Disposition` set edilmelidir.
  • Malware scanning/quarantine gerekiyorsa dosyayı kullanıma açmadan önce pipeline'a koyun; scanner başarısızlığını başarı gibi ele almayın.

Önlem mimaride nereye oturur?

Gateway/container limitleri request boyutunu; controller upload contract'ını; service allowlist, ownership ve processing işini; storage katmanı path/izin/retention'ı; download response content policy'yi yönetir. Tek bir MIME check yeterli değildir. Defense in depth, dosyanın kabul edilmesinden tüketilmesine kadar tüm yaşam döngüsünü kapsar.

C++ Karşılığı
• C++ servisinde upload byte'ını sınırlı stream olarak alın; tüm dosyayı sınırsız belleğe yüklemeyin.
• Filename'den path üretmeyin; generated name ve webroot dışı private storage kullanın.
• Image parser/decompressor'a size, dimensions ve CPU limitleri uygulayın.
• `std::filesystem` ile canonical path doğrulaması yapın; symlink/TOCTOU riskini ayrıca değerlendirin.
• RAII ile geçici dosya/descriptor temizliğini garanti edin.
• Fuzzing ve sanitizer ile dosya parser'ı test edin.

Sık yapılan hatalar ve kontrol listesi

  • Dosya uzantısına veya client MIME header'ına güvenmek.
  • Client filename'ini path'e birleştirmek.
  • Upload size limitini yalnızca UI tarafında uygulamak.
  • Image dimensions/decompression sınırını atlamak.
  • SVG'yi güvenli raster image gibi sunmak.
  • Dosyayı webroot altında/execute edilebilir izinle saklamak.
  • Scan/decoder hata verince dosyayı kabul etmek.
  • Temp dosya ve quarantine lifecycle'ını unutmak.

Mini sorular

1. `image/png` header'ı ve `.png` uzantısı dosyanın güvenli PNG olduğunu kanıtlar mı?

Hayır. İkisi de client tarafından gönderilebilir; server-side decoder/content validation ve limit gerekir.

2. Görseli decode edip yeniden encode etmek ne sağlar?

İzin verilen pixel verisinden yeni çıktı üretip metadata/ek payload riskini azaltır; decoder açıklarını veya kaynak tüketimini tek başına çözmez.

3. Projede hangi upload endpoint'ini bugün test edebiliriz?

Hiçbiri görünmüyor. Öneri endpoint `/demo/files`; önce demo controller ve güvenli storage tasarımı eklenmeli.
