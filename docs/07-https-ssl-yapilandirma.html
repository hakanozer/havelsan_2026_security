Transport security · OWASP A02 / A05

Enforcing HTTPS ve TLS yapılandırması

HTTPS, istemci ile TLS sonlandırma noktası arasındaki trafiğin gizliliğini, bütünlüğünü ve sunucu kimliğinin doğrulanmasını sağlar. Basic credentials, session cookie ve hassas API verisi HTTP üzerinde taşınırsa ağ üzerindeki dinleyici bunları görebilir/değiştirebilir. Projede HTTP portu tanımlanmış; uygulama SSL/TLS ayarı görünmüyor.

Neden önemli?

HTTP trafiğinde ağ yolu üzerindeki bir kişi/ara sistem isteği okuyabilir veya değiştirebilir. Basic Authentication kullanıcı ve parolayı her istekte Base64 biçiminde taşır; Base64 şifreleme değildir. Session cookie çalınırsa kullanıcı adına işlem yapılabilir. TLS bu ağ bağlantısını korur ancak uygulama authorization, güvenli storage veya endpoint validation sorunlarını çözmez.

Kritik/savunma ortamında sertifika zinciri, hostname doğrulaması, anahtar erişimi/rotasyonu ve TLS sonlandırma mimarisi konfigürasyon yönetiminin parçasıdır. OWASP ASVS'nin transport security kontrolleri ve NIST TLS rehberi referans olarak kullanılabilir; kurum profili ayrıca doğrulanmalıdır.

Saldırı nasıl çalışır?

  1. İstemci HTTP ile credential, cookie veya iş verisi gönderir.
  2. Aradaki ağ bileşeni trafiği görebilir/değiştirebilir.
  3. Credential/session ele geçirilirse saldırgan API'yi kullanabilir veya response'u manipüle edebilir.
  4. TLS sertifikayı doğrulayarak şifreli kanal kurar; HTTP→HTTPS yönlendirme ve HSTS, ilk/sonraki isteklerde downgrade riskini azaltır.
  5. Reverse proxy TLS sonlandırıyorsa proxy→uygulama ağı da güven sınırı olarak korunur.

Projemizde nerede?

src/main/resources/application.properties:1-18 içinde `server.port=8090` var; SSL konfigürasyonu görünmüyor. CorsConfig.java:12-19 allowlist'inde HTTPS origin yer alıyor; bu yalnızca tarayıcı origin politikasına ilişkindir, server TLS listener'ı açmaz.

SecurityConfig.java:24-33 HTTP Basic kullanıyor. Projede HTTPS yoksa gerçek kimlik bilgileriyle uzak ağda test yapılmamalıdır.

SONRA (Önerilen Düzeltme / iki dağıtım seçeneği)

Projede HTTPS configuration yok. TLS edge proxy/load balancer'da sonlandırılabilir veya uygulamanın embedded server'ında etkinleştirilebilir. Aşağıdaki Spring Boot properties sadece öneridir; sertifika/keystore dosyası ve secret yönetimi deploy ortamına göre sağlanmalıdır.

server.port=8443server.ssl.enabled=trueserver.ssl.key-store=${TLS_KEY_STORE}server.ssl.key-store-password=${TLS_KEY_STORE_PASSWORD}server.ssl.key-store-type=PKCS12server.ssl.key-alias=${TLS_KEY_ALIAS}
DikkatPlaceholder değerlerini source control'a koymayın. TLS terminasyonu reverse proxy'de ise forwarded headers, proxy trust listesi ve proxy→app ağı güvenli biçimde yapılandırılmalı; dışarıdan gelen sahte forwarded header'a güvenilmemelidir.

Minimum ekleme önerisi

Uygulama TLS key material'ını local/dev secret'tan alacak şekilde profilli HTTPS portu ekleyin veya yerel reverse proxy kullanın. Sertifika oluşturma/keystore provisioning yöntemini eğitmen ortamına göre seçin ve doğrulayın; bu repoda sertifika bulunmadığından çalışır bir HTTPS endpoint yoktur.

  1. Önce şu anki HTTP endpoint'ini loopback'te gözlemleyin; yalnızca test credential kullanın.
  2. Yerel CA tarafından imzalı sertifikayla TLS listener'ı başlatın (self-signed certificate ise güven zinciri ayrıca kurulur; client verification bypass etmeyin).
  3. İstemciyle sertifika zinciri/hostname doğrulamasını etkin tutarak istek gönderin; TLS version/cipher policy kurum gereksinimine göre doğrulanır.
  4. HTTP listener gerekiyorsa yalnızca HTTPS'ye yönlendirin; prod'da HSTS'i doğru domain/scope kararıyla ekleyin.
# Mevcut local HTTP endpoint (gizli veri kullanmayın):
curl -i http://localhost:8090/customer/login

# ÖNERİLEN kurulumdan sonra, güvenilen local CA ile:
curl --cacert ./local-ca.pem -i https://localhost:8443/customer/login

İkinci komut önerilen yapılandırma içindir; endpoint/port/CA dosyası henüz projede yoktur. `-k/--insecure` kullanmak sertifika doğrulamasını devre dışı bırakarak demoda öğretilen korumayı boşa çıkarır.

Önlem mimaride nereye oturur?

TLS uygulama sunucusunda veya ingress/reverse proxy'de; sertifika ve özel anahtar yönetimi platform/secret store'da; HSTS/redirect web edge veya response header katmanında yer alır. TLS tek başına XSS, SQLi, yetki bypass veya yanlış loglama riskini çözmez. Neden sadece Basic'i JWT ile değiştirmek değil? Token da HTTP üzerinden giderse çalınabilir; taşıma şifrelemesi kimlik yönteminden bağımsız gereklidir.

C++ Karşılığı
• C++ HTTP servisinin public ağ trafiğinde TLS zorunludur; sertifika ve hostname doğrulaması korunur.
• TLS'i güvenilir reverse proxy'de sonlandırıyorsanız backend ağını ve forwarded-header trust'ını da sınırlandırın.
• OpenSSL gibi kütüphaneyi doğrudan kullanıyorsanız protokol/certificate verification ayarlarını güncel rehberle doğrulayın.
• TLS anahtarını kaynak koda veya loga koymayın; secret store ve rotasyon kullanın.
• C++ framework'ünün TLS API'sini varsaymayın; seçilen sürüme göre doğrulayın.
• Operasyonel TLS taraması ve sertifika yenileme testi planlayın.

Sık yapılan hatalar ve kontrol listesi

  • CORS origin'inde HTTPS görünmesini server TLS'i var sanmak.
  • Basic credential'ı plaintext HTTP üzerinden göndermek.
  • Self-signed test için her client'ta sertifika doğrulamasını kapatmak.
  • Private key/keystore parolasını repoya yazmak.
  • Proxy TLS terminasyonunu unutup internal hop'u korumasız bırakmak.
  • HSTS'i test domaininde yanlış kapsamla açmak.
  • Sertifika sona erme/rotasyon izlemesini yapmamak.

Mini sorular

1. HTTPS CORS'un diğer adı mıdır?

Hayır. HTTPS TLS taşıma güvenliğidir; CORS browser'ın cross-origin response erişim politikasını belirler.

2. HTTP Basic parola verisini şifreler mi?

Hayır. Base64 encoding kullanılır; TLS olmadan gizlilik sağlamaz.

3. `curl -k` ile TLS testi yapmak neden yanlış sinyal verir?

Sertifika doğrulamasını devre dışı bırakır; yanlış/başka sertifika kullanan sunucuyu ayırt edemezsiniz.
