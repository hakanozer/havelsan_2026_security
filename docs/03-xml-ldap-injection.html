XML Injection ve LDAP Injection

XML Injection, kullanıcı girdisinin XML metnine bağlamı korunmadan eklenip belgenin yapısını değiştirmesine; LDAP Injection ise girdinin LDAP filter sözdizimine karışmasına dayanır. İki parser'ın escaping/sözdizimi farklıdır. Projede XML tabanlı bir REST akışı veya LDAP istemcisi yok; ayrı XXE örneği bu başlıkların yerine geçmez.

Neden önemli?

XML/LDAP injection'da uygulama, dış girdiyi yapılandırılmış bir dilin parçası olarak yorumlanacak yere taşır. Girdi bir alan değeri olmaktan çıkıp node, predicate veya filter koşuluna dönüşürse sonuç kümesi genişleyebilir, beklenmeyen veri görünür olabilir ya da iş kuralı atlanabilir. Kurumsal directory'de bu, kullanıcı/grup arama sonuçlarının bütünlüğünü ve gizliliğini etkileyebilir.

Önlem parser'a uygun parametreleme veya encoder kullanmaktır. Genel blacklist alternatifi güvenilir değildir: izin verilen karakterleri değil, bilinmeyen sözdizim varyantlarını yakalamaya çalışır.

Saldırı nasıl çalışır?

XML Injection

  1. Uygulama kullanıcı metnini XML etiketleri arasında string birleştirerek yazar.
  2. Girdi XML metacharacter/etiket sınırını değiştirir.
  3. XML parser farklı bir element/attribute ağacı üretir; uygulama başka bir alanı veya kaydı işler.

LDAP Injection

  1. Uygulama arama filtresini `(&(uid=...)(active=true))` gibi bir template ile string oluşturur.
  2. Kontrol edilmeyen girdi LDAP filter gramerini etkiler.
  3. Directory sunucusu daha geniş/başka bir filtre çalıştırır ve sonuçlar uygulamanın varsaydığından farklı olur.
İpucuXML Injection ile XXE aynı şey değildir. XXE, parser'ın external entity/DTD çözümlemesinin doğurduğu belirli bir XML parser riskidir; ayrı ders sayfası 04 · XXE.

Projemizde nerede?

LDAP bağlantısı, LDAP filter sorgusu, XML REST endpoint'i veya XML payload'ı kabul eden controller bulunmadı. En yakın gerçek kaynak ayrı komut satırı SAX örneği src/main/java/xxe/MainXml.java:6-29 ve fixture src/main/resources/staff.xml:1-16; bu örnek XXE parser yapılandırması içindir ve LDAP/XML Injection endpoint'i değildir.

REST endpoint'leri [CustomerController.java](../src/main/java/com/works/controller/CustomerController.java), [ProductController.java](../src/main/java/com/works/controller/ProductController.java), [NoteController.java](../src/main/java/com/works/controller/NoteController.java) kapsamında JSON alır.

ÖNCE / SONRA: projede karşılığı yok

ÖNCE (zayıf proje kodu): Bu iki zafiyete ait proje kodu yok; gerçek dosya yolu/metot uydurulamaz. Dolayısıyla zayıf kod alıntısı verilmemiştir.

SONRA (güvenli ilke): XML için string concatenation yerine XML writer/binding API'nin text/attribute değerlerini ayrı yazma mekanizmasını kullanın. LDAP için filter değerlerini LDAP filter gramerine göre kaçışlayabilen, doğrulanmış bir kütüphaneyi kullanın; filtre template'ini kullanıcı girdisiyle birleştirmeyin. Gerçek sınıf/metot seçimi, kullanılacak LDAP/XML kütüphanesine göre doğrulanmalıdır.

DikkatXML verisini güvenli oluşturmak XXE'yi otomatik kapatmaz; parser konfigürasyonunda external entity/DTD davranışını ayrıca kısıtlayın. Bunun tersi de geçerli: XXE hardening, XML Injection'ı önlemez.

Önlem nerede durur?

XML üretiminde serialization/escaping uygulama katmanında; XML parse ederken parser konfigürasyonu veri giriş sınırında; LDAP filter üretimi directory adapter/repository katmanında yer alır. Controller validation, izinli uzunluk ve iş formatını denetler ama parser'a uygun escaping'in yerini almaz. Birlikte kullanıldığında her dil sınırında doğru encoding gerekir.

C++ Karşılığı
• C++ XML kütüphanesinde node/text API kullanın, XML'i ham concatenation ile üretmeyin.
• LDAP istemcisinde filter value escaping için seçilen kütüphanenin doğrulanmış helper'ını kullanın; API adı kütüphaneye göre teyit edilmeli.
• Girdiyi allowlist ve uzunluk sınırıyla doğrulayın; validation tek başına encoding değildir.
• C/C++ string buffer uzunluğu ve ömrünü sınırlandırın; `std::string` tercih edin.
• Kütüphane güvenlik ayarlarını (external entity/DTD) ayrıca yapılandırın.
• `clang-tidy`, `cppcheck`, sanitizer ve parser testleriyle doğrulayın.

Sık yapılan hatalar ve kontrol listesi

  • XXE ile XML Injection'ı aynı zafiyet saymak.
  • XML'i string birleştirerek kurmak ve yalnızca `<`/`>` blacklist'i kullanmak.
  • LDAP filter değerini DN escape kuralıyla kaçışlamak; bağlamların farklı olduğunu unutmak.
  • Input allowlist'i uygulayıp parser escaping'i atlamak.
  • LDAP arama hesabına gereğinden fazla directory yetkisi vermek.
  • Üretim directory'sine eğitim payload'ı göndermek.
  • Öneri sınıf/endpoint'ini projede zaten varmış gibi dokümante etmek.

Mini sorular

1. XXE önlemi XML Injection'ı otomatik önler mi?

Hayır. XXE parser'ın dış entity/DTD çözümlemesiyle; XML Injection ise girdinin XML yapısına karışmasıyla ilgilidir.

2. LDAP filter için genel SQL escaping kullanmak doğru mudur?

Hayır. LDAP filter ve SQL farklı gramerlerdir; LDAP bağlamına uygun escaping/parameterization gerekir.

3. Bu projede LDAP injection'ı hangi endpoint'te gösterebiliriz?

Mevcut endpoint yok. Demo önerisi `com.works.demo.LdapInjectionDemoController` ve `/demo/ldap/search`; mock directory ile eklenmelidir.
