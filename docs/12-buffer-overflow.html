Native memory safety · Java bounds are different

Buffer Overflow

Buffer Overflow, native programın ayrılmış belleğin sınırını aşan okuma/yazma yapmasıdır. Java dizileri ve ByteBuffer'lar bounds check uygular; tipik sonuç bellek üzerine yazma değil, exception'dır. Projede JNI/native C++ yok, ancak kripto kodu ByteBuffer ile IV ve ciphertext'i paketleyip ayırıyor; C++ güvenliğinin ağırlığı bu sayfada.

Okuma süresi: 24 dkHedef: Java/Spring Boot + C++ geliştiricileriCWE-120 · CWE-787
Bu konu projede henüz yokJava kaynaklarında JNI/native C++ modülü bulunmuyor. Ek olarak, ByteBuffer parse kodu malformed input'ta bounds exception verebilir; bu native buffer overwrite değildir. C++ demo bu repo'ya entegre değil.

Neden önemli?

Native C/C++ buffer'ında uzunluk kontrolü eksikse bitişik belleğe yazma/okuma; çökme, veri bozulması veya güvenlik sınırlarının aşılması gibi sonuçlara yol açabilir. Etki derleyici, işletim sistemi, bellek düzeni ve kontrol akışına bağlıdır; burada exploit tekniği anlatılmayacaktır.

Java managed heap bounds check ile farklı güvenlik özelliği sağlar, fakat JNI, direct/off-heap memory, native image codec/crypto kütüphanesi ve boyut hesaplama hataları native riskleri sisteme geri sokabilir. ASLR/DEP gibi mitigations, doğru bounds kontrolünün alternatifi değildir.

Saldırı nasıl çalışır?

  1. Native kod sabit/hesaplanmış kapasitede buffer ayırır.
  2. Girdi uzunluğu doğrulanmadan buffer'a kopyalanır veya index hesaplanır.
  3. Yazma/okuma ayrılan aralığın dışına taşar.
  4. Yanındaki data bozulur, program abort eder veya hatalı memory access oluşur.
  5. Container tipi, bounds-checked API, integer overflow checks, fuzz/sanitizer testleri bu hatayı build/test aşamasında yakalar.

Projemizde nerede?

Projede native C++/JNI kodu yok. Java ByteBuffer kullanımı AES-GCM IV + ciphertext birleştirme ve parse etme amacıyla CryptoService.java:27-58, 68-101 aralığında.

ByteBuffer relative `get`/`put` sınırı aşıldığında Java runtime buffer exception üretir; bu bellek sınırını aşan native overwrite ile aynı değildir. `decrypt` kısa/bozuk veride exception oluşturabilir ve catch ile RuntimeException olarak sarılır; malformed input handling test edilmelidir.

ÖNCE (projede mevcut: buffer paketleme)

Aşağıdaki gerçek kod fixed IV uzunluğunu ve ciphertext'in kalanını ByteBuffer'a paketler. Bu satırlar Buffer Overflow açığı değildir; girdi boyu/formatı sınırı ve malformed buffer davranışını incelerken kullanılır.

Kaynak: src/main/java/com/works/service/CryptoService.java:53-57, 72-83

ByteBuffer buffer =        ByteBuffer.allocate(iv.length + encrypted.length);buffer.put(iv);buffer.put(encrypted);ByteBuffer buffer = ByteBuffer.wrap(data);byte[] iv = new byte[IV_LENGTH];buffer.get(iv);byte[] cipherText = new byte[buffer.remaining()];buffer.get(cipherText);

Not: `buffer.get(iv)` için decoded data IV'den kısa ise Java exception verir. Bu native overwrite değildir; giriş formatını doğrulayıp hatayı kontrollü biçimde yönetmek ve test etmek gerekir.

SONRA (Önerilen Düzeltme)

Project source'ta minimum length/version/format guard görünmüyor. Önerilen akış; Base64 decode sonrası `data.length` en az sabit IV + minimum valid ciphertext/tag uzunluğunda mı kontrol edin, sonra buffer parse edin; hatalı girdiye kontrollü client error verin. Kriptografik authentication tag doğrulaması yine `doFinal` ile yapılmalıdır; yalnızca uzunluk kontrolü ciphertext'in geçerli olduğunu kanıtlamaz.

if (data.length < IV_LENGTH + minimumTagBytes) rejectMalformedInput();ByteBuffer buffer = ByteBuffer.wrap(data);byte[] iv = new byte[IV_LENGTH];buffer.get(iv);

Bu bir öneri taslağıdır; project API'sine eklenmiş kod değildir. `minimumTagBytes` AES-GCM tag length/config ile tutarlı belirlenmeli, Java exception sınırları kullanıcıya hassas ayrıntı döndürmemelidir.

Önlem mimaride nereye oturur?

Native boundary'de parser ve buffer API'si; Java/native interface'te length/type contract; CI'da compiler hardening, sanitizer ve fuzzing uygulanır. Java ByteBuffer bounds check'i native pointer arithmetic'i korumaz. Integer overflow ile buffer allocation size hesabını da kontrol edin.

C++ Karşılığı
• Güvensiz pattern: sabit boyutlu `char` buffer'a uzunluğu doğrulanmamış C-string kopyalamak; exploit/payload örneği burada verilmez.
• Modern çözümde `std::string`, `std::vector`, `std::array`, `std::span` ve bounds-checked erişim kullanın.
• `strcpy`, `sprintf`, `gets` gibi sınırsız fonksiyonlardan kaçının; `snprintf` de dönüş/uzunluk kontrolü gerektirir.
• RAII sahipliği, integer range kontrolü ve input length limitleri ekleyin.
• AddressSanitizer, UBSan, `-fstack-protector`, `_FORTIFY_SOURCE` ve platform ASLR/DEP ek katmandır.
• `clang-tidy`, `cppcheck` ve fuzzing native boundary'leri doğrular.

Sık yapılan hatalar ve kontrol listesi

  • Java BufferUnderflow/Overflow exception'ını native memory corruption sanmak.
  • Native/JNI çağrısına giden uzunluğu doğrulamamak.
  • `capacity` ve `limit` semantiğini karıştırmak.
  • Allocation boyutu hesaplanırken integer overflow'ı atlamak.
  • Sanitizer kullanıp input sınır testlerini yazmamak.
  • Mitigation'ları bounds check yerine koymak.
  • Kaynağa özel exploit payload'ı üretip demo kapsamını aşmak.

Mini sorular

1. Java ByteBuffer'ın sınır dışı erişimi C++ buffer overflow ile aynı mı?

Hayır. Java ByteBuffer relative erişimde runtime bounds exception üretir; native C++ pointer/array sınır aşımı bellek bozulmasına yol açabilir.

2. AddressSanitizer production input validation yerine geçer mi?

Hayır. Test/build aşamasında memory bug'ı saptar; sınır kontrolü ve güvenli API yine gerekli.

3. Projede hangi JNI endpoint'ini kullanabiliriz?

Yok. C++ önerisi `demos/cpp/BufferBoundsDemo.cpp`; web wrapper istenirse ayrı ve local-only öneri olarak eklenmelidir.
