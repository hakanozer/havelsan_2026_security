XML parser güvenliği · OWASP A05:2021 Security Misconfiguration

XXE (XML External Entity)

XXE, XML parser'ın DOCTYPE/external entity tanımlarını etkin bırakıp dış kaynakları çözümlemesiyle ortaya çıkabilir. Saldırgan belge içindeki entity üzerinden uygulamanın erişebildiği dosya veya servisleri okutmayı ya da kaynak tüketimini tetiklemeyi hedefler. Projede test fixture'ında entity referansı vardır; SAX parser dış entity/DTD kullanımını kapatmıştır.

Neden önemli?

XML parser, external entity çözümlemesini uygulama sunucusunun kimliği ve ağ erişimleriyle yapabilir. Hatalı yapılandırma, uygulamanın okuyabildiği dosyaları açığa çıkarma, iç ağ adreslerine istek gönderme veya entity expansion ile kaynak tüketme riski taşır. Etkinin sınırı parser, işletim sistemi izinleri, ağ politikası ve işlenen XML'e bağlıdır.

Kritik yazılımlarda XML'i güven sınırı dışından almak için parser güvenli varsayılanlarını doğrulamak ve dış erişimi ayrıca kısıtlamak gerekir. OWASP ASVS ve CWE-611 bu riskin kontrol/test bağlamı için referans olabilir.

Saldırı nasıl çalışır?

  1. Uygulama güvenilmeyen XML'i parser'a verir.
  2. Parser DOCTYPE ve external entity tanımlarına izin verir.
  3. Belge, external entity referansıyla parser'ın yetkili olduğu bir kaynağı işaret eder.
  4. Parser kaynağı çözümleyip entity içeriğini uygulama verisine ekler veya dış erişim/kaynak tüketimi yaratır.
  5. DOCTYPE ve external entity/DTD özelliğini kapatmak bu çözümleme adımını keser.
DikkatPayload içeriğini yalnızca kaynağın eğitim fixture'ında okuyup parser davranışını yerel olarak gözlemleyin. Kasıtlı zayıf parser'ı gerçek veri veya ağ erişimi olan ortama bağlamayın.

Projemizde nerede?

Ayrı SAX komut satırı örneği src/main/java/xxe/MainXml.java:6-29; test XML'i src/main/resources/staff.xml:1-16. Bu bir REST endpoint'i değildir.

ÖNCE (fixture: external entity tanımı)

Aşağıdaki satırlar parser kodu değil, test verisidir. Gerçekten zayıf parser burada bulunmuyor; örnek SAX kodu güvenli yapılandırma içeriyor.

Kaynak: src/main/resources/staff.xml:1-5

<?xml version="1.0" encoding="utf-8"?><!DOCTYPE foo [ <!ENTITY xxe SYSTEM "file:///etc/passwd" > ]><Company>    <staff id="1001">        <name>&xxe;</name>

Bu input yalnız başına açığı kanıtlamaz: sonucu parser yapılandırması belirler. Bu projede fixture test amaçlı olsa da harici dosyayı işaretlediğinden yerel olmayan sistemlerde çalıştırılmamalıdır.

SONRA (projede mevcut güvenli parser yapılandırması)

Kaynak: src/main/java/xxe/MainXml.java:12-23

SAXParserFactory factory = SAXParserFactory.newInstance();factory.setFeature("http://apache.org/xml/features/disallow-doctype-decl", true);factory.setFeature("http://xml.org/sax/features/external-general-entities", false);factory.setFeature("http://xml.org/sax/features/external-parameter-entities", false);factory.setFeature("http://apache.org/xml/features/nonvalidating/load-external-dtd", false);SAXParser saxParser = factory.newSAXParser();saxParser.parse(FILENAME, handler);

Neden işe yarar? DOCTYPE reddedilir; external general/parameter entity ve external DTD yükleme devre dışı bırakılır. Böylece parser'ın dış kaynağı çözümlemesi önlenir. İlgili feature bu parser sağlayıcısında desteklenmiyorsa uygulama güvenli moda geçtiğini varsaymamalı; başlatma hatası açıkça ele alınmalı ve sağlayıcı test edilmelidir.

Canlı demo adımları

  1. Proje kökünde Java 17 ve Maven ile sınıfları derleyin. Maven wrapper destek dosyaları bu checkout'ta olmadığından `mvn` komutu kullanılmalıdır.
  2. Ayrı main sınıfını yerel olarak çalıştırın. Kaynaktaki test XML'i DOCTYPE nedeniyle parser tarafından reddedilmeli; dış dosyanın içeriği `name` alanına eklenmemelidir.
  3. Parser hata mesajını gözlemleyin. `MainXml` exception'ı `printStackTrace()` ile konsola yazar; bu örnek REST yanıtına dönmez.
  4. Parser sağlayıcı/Java sürümünü değiştirdiğinizde feature ayarlarının gerçekten uygulandığını aynı fixture ile test edin.
mvn -q -DskipTests compile
java -cp target/classes xxe.MainXml
# Beklenti: DOCTYPE reddedilir; dış entity içeriği yazdırılmaz.
DikkatBu demo yalnızca eğitim checkout'unda, yerel ortamda çalıştırılmalıdır. Kaynak XML içindeki `file:///etc/passwd` harici bir hedefe istek değildir; yerel dosya referansıdır. Herhangi bir dosya içeriğinin açığa çıkmasını amaçlamayın.

Önlem mimaride nereye oturur?

XXE önlemi XML parser/factory oluşturulduğu noktada, yani input parsing sınırında durur. Controller validation bunu tek başına çözmez; dosya/URL izinleri ve container egress politikaları ek savunma katmanlarıdır. Dış entity'yi kapatmak, XML Injection, XML bombası için tüm parser kaynak limitleri veya iş kuralı kontrollerini otomatik sağlamaz.

DOCTYPE tamamen gerekmiyorsa kapatmak, sadece bilinen zararlı ifadeleri kara listelemekten daha doğru bir sınır koyar: kapatılacak capability net ve parser feature'ı ile test edilebilir.

C++ Karşılığı
• C++ XML parser'larında external entity/DTD çözümlemesini varsayılanlara bırakmayın.
• Kullandığınız parser kütüphanesinin güvenli ayar API'sini kendi sürüm dokümanından doğrulayın.
• Girdiye boyut/derinlik limiti koyun ve dosya/ağ erişimini daraltın.
• XML'i string concatenation ile üretmeyin; writer'ın text/attribute API'sini kullanın.
• C++ için SEI CERT ve kütüphane güvenlik advisories'lerini takip edin.
• Fuzzing ve sanitizer testleri parser sınır koşullarını bulmaya yardımcı olur.

Sık yapılan hatalar ve kontrol listesi

  • Sadece external entity'yi kapatıp external DTD yüklemeyi unutmak.
  • DOCTYPE içeren fixture'ı güvenli parser kanıtı sanmak veya tersi.
  • Feature set başarısız olduğu halde parser ile devam etmek.
  • JDK/parser sağlayıcısı sürümünde ayarların etkisini test etmemek.
  • XXE'yi XML Injection ile aynı kabul etmek.
  • Exception stack trace'ini HTTP response'a göndermek.
  • Parser için ağ erişimini ve dosya izinlerini sınırsız bırakmak.

Mini sorular

1. `staff.xml` içinde external entity olması uygulamanın XXE'ye açık olduğunu kanıtlar mı?

Tek başına hayır. Parser'ın DOCTYPE ve external entity ayarları belirleyicidir; projedeki SAX örneği bunları kapatıyor.

2. DOCTYPE ve external entity kapalı olsa da input limitleri gerekli midir?

Evet. Boyut, derinlik ve işlem süresi kontrolleri diğer parser kaynak tüketimi risklerine karşı ayrı savunmadır.

3. XML'i güvenli serialize etmek XXE önler mi?

Hayır. Serialization XML Injection riskini azaltır; XXE için parser'ın entity/DTD çözümlemesini ayrıca sınırlandırmak gerekir.
