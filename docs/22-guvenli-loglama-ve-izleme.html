Audit evidence without leaking credentials

Güvenli Loglama ve İzleme

Loglar olay inceleme ve servis sağlığı için kanıt sağlar; kontrolsüz loglama session/token, kişisel veri veya attacker-controlled metin sızdırabilir. Log injection, satır ayırıcı/format kontrolü olmayan input'un sahte event gibi görünmesine yol açabilir. Projede `logs/application.log` dosya appender'ı var ve filter session ID, username, role, User-Agent ve IP logluyor.

Neden önemli?

Log event'leri bir incident'ta ne olduğunu anlamayı sağlar; fakat session token veya credential loga yazılırsa aynı event store saldırgan için credential kaynağı olur. Untrusted header/path values newline veya control karakterleriyle formatı bozabilir; operatör sahte event'i gerçek sanabilir. Aşırı log da maliyet, disk tüketimi ve veri saklama riskidir.

Kritik/savunma ortamında log integrity, access control, time sync, retention, export ve incident handling planı audit gereksinimleriyle uyumlu olmalıdır. OWASP Logging Cheat Sheet ve CWE-117 log injection konusunda referans olabilir.

Saldırı nasıl çalışır?

  1. Filter/header/path/user input gibi attacker-controlled value log mesajına girer.
  2. Encoder control chars/CRLF'i yapılandırılmış alan olarak güvenli kaçışlamaz veya sensitive token loglanır.
  3. Event sahteleşir ya da session credential log read access'i olan kişilere açılır.
  4. Log kopyası/backup/central collector'da erişim süresi uzar; olay etkisi büyür.
  5. Structured logging, field allowlist, CR/LF normalization, secret redaction, least-privilege storage ve retention kontrolü riski düşürür.

Projemizde nerede? `logs/` klasörü ne işe yarar?

  • Aktif log yolu ve günlük rollover: logback-spring.xml:4-5, 17-47.
  • File appender `logs/application.log` yazar; günlük dosya adı ve maxHistory 30 gün: lines 21-45.
  • File appender yalnızca `com.works.config.FilterConfig` logger'ına bağlı; root logger console appender kullanıyor: lines 51-62.
  • Filter request URL, username, roles, time, User-Agent, IP, SessionId logluyor: FilterConfig.java:51-67.
  • Workspace'teki mevcut logs/application.log dosyası boş; runtime'da içeriği değişebilir.

Bu nedenle logs klasörü runtime diagnostic/audit mesajlarını tutan uygulama dizinidir; iş verisi/credential arşivi olarak tasarlanmamıştır. Dosya permissions ve deployment'taki mount/retention ayrıca kontrol edilir.

ÖNCE (projede mevcut: session metadata loglama)

Parameterized SLF4J kullanımı log format interpolation sorununu azaltır; ancak session ID ve attacker-controlled metadata'nın loglanmasını tek başına güvenli yapmaz. Session ID bearer secret olarak ele alınmalı.

Kaynak: src/main/java/com/works/config/FilterConfig.java:54-67

String agent = xssReq.getHeader("User-Agent");String ip = xssReq.getRemoteAddr();String sessionId = xssReq.getSession().getId();log.info("URL: {}, Username: {}, Roles: {}, Time: {}, Agent: {}, IP: {}, SessionId: {}",        url, username, roles, time, agent, ip, sessionId);

SONRA (Önerilen Düzeltme)

Projedeki filter logger için redacted alternatif yok. Secret/session ID'yi tamamen çıkarın; gerekli audit event'ini allowlisted fields ile structured formatta yazın. User-Agent/URL gibi untrusted field'ları newline/control chars açısından normalize/escape edin. Öneri örneği proje kodu değildir:

log.info("requestId={}, path={}, user={}, outcome={}",        correlationId, safePath, pseudonymousUser, outcome);// No session ID, password, token, or raw request body.

Canlı demo adımları

  1. Uygulamayı local'de çalıştırın ve `logs/application.log` file creation/content davranışını gözleyin; mevcut tracked dosya boş olabilir.
  2. `GET /product/list` isteğiyle FilterConfig log event'i üretin. Rate limiter eşiğini aşmayın; her request'in SessionId alanına bakın ama değeri kopyalamayın.
  3. Header'da benign printable test değeri verip log formatını inceleyin; CR/LF injection payload'ı çalıştırmayın.
  4. Logback'te FilterConfig appender file'a, root'un yalnız console'a bağlı olduğunu gösterin; root loglarının dosyaya yazıldığını varsaymayın.
  5. Öneri sonrası test, log record içinde SessionId/token/password olmadığını ve untrusted field'ın tek kayıt olarak güvenli encode edildiğini assert etmeli.

Retention, access ve redaction

  • Session ID, Authorization header, password, token, encryption key ve request body'yi varsayılan olarak loglamayın.
  • Path/query/UA gibi untrusted value'ları structured field olarak encode edin; newline/control char normalization uygulayın.
  • Log dizini ve central collector'a least-privilege access; encrypted transport/storage ve audit.
  • Retention süresi iş/uyum ihtiyacına göre belirlenmeli. Projede daily rollover `maxHistory=30` var; bu 30 günlük saklama sınırını platform backup policy ile birlikte doğrulayın.
  • Clock sync, request correlation ID ve incident timeline'ı secretsiz üretin.
  • Logging failure'ı silent success gibi ele almayın; availability ve secure degradation policy tasarlayın.

Önlem mimaride nereye oturur?

Application logger event içeriğini; Logback encoder/appenders biçim/rotation'ı; OS/container file permission'ları erişimi; central collector retention/access/audit'i yönetir. Redaction source'ta başlar ve downstream sink'te tekrar kontrol edilir; bir sink'teki masking diğer appender'a otomatik uygulanmayabilir.

Neden session ID yerine correlation ID? Incident trace için correlation ID event bağlar fakat authentication credential değildir. Log access'i hâlâ kontrollü olmalıdır.

C++ Karşılığı
• User-controlled strings'i raw format string'e vermeyin; structured logging API kullanın.
• CR/LF/control char'ları log field'larında encode edin; forged record riskini azaltın.
• Session/token/password/key ve raw payload'ı loglardan çıkarın/redact edin.
• Log file permissions, rotation, retention ve collector access'i sınırlandırın.
• RAII/error policy ile logging failure ve secret buffer yaşam süresini yönetin.
• `clang-tidy`/SAST ile sensitive data logging pattern'lerini review edin.

Sık yapılan hatalar ve kontrol listesi

  • Session ID/token'ı debug kolaylığı için loglamak.
  • Parameterized logger kullanınca log injection'ın tamamen bittiğini sanmak.
  • File appender'ın root logger'a bağlı olduğunu varsaymak.
  • Retention değerini platform backup/central collector'dan bağımsız yorumlamak.
  • User-Agent, path ve username'i güvenilir input kabul etmek.
  • Production loglarını eğitim materyaline veya issue'ya eklemek.
  • Log schema'ya gereğinden fazla PII eklemek.

Mini sorular

1. Projede hangi loglar `logs/application.log` dosyasına yazılıyor?

Logback config'te günlük file appender FilterConfig logger'ına bağlı; root logger console'a bağlıdır.

2. Parameterized SLF4J log çağrısı log injection riskini otomatik çözer mi?

Hayır. Format string separation'a yardım eder; attacker-controlled newline/control characters encoder/structured field düzeyinde ele alınmalıdır.

3. Session ID yerine incident tracing için ne kullanılabilir?

Authentication credential olmayan, secretsiz correlation/request ID; ayrıca log erişimi ve retention yine sınırlandırılır.
